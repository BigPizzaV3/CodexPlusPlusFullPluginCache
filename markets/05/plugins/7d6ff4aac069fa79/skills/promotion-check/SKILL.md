# Promotion Check

在编码完成后检查真实代码变更，帮助前端 RD 准备联调、跟踪证据并判断 CR 准备度。默认只读分析；除非用户另行要求，不修改代码、不调用会改变业务数据的接口、不提交代码或创建 CR。

## 意图路由

只读取命中模式所列的文件，不预加载其他参考文件。

| 用户意图与常见表达 | 模式 | 读取文件 | 最低输入与缺失处理 |
|---|---|---|---|
| “生成/补充联调清单”“能开始联调吗” | 联调准备 | [integration-preparation.md](references/integration-preparation.md) 和 [checklist.md](references/checklist.md) | 需要可识别的代码变更范围；优先从 Git 推断，仍无法收窄时再询问 |
| “这个请求为什么失败”“联调卡住了”“帮我看这段响应/日志/截图” | 联调协助快速路径 | [integration-assistance.md](references/integration-assistance.md) | 需要现象或一项真实证据；不足时只追问最能缩小范围的一项 |
| “现在能提 CR 吗”“提交前再检查一次”“做 CR 前复检” | CR 前复检 | [cr-review.md](references/cr-review.md) 和 [checklist.md](references/checklist.md) | 需要最新变更范围；联调或命令证据缺失时可以检查，但必须分别输出准备度和动作建议 |
| 普通业务、代码知识或页面操作问答 | 不执行工作流 | 不读取参考文件 | 直接回答，不扫描仓库、不维护台账 |
| “帮我看看”等无法判断阶段的表述 | 兜底 | 不读取参考文件 | 先确认是准备联调、排查单个问题，还是 CR 前复检 |

用户同时要求多个结果时，以最终目标选择路径：包含“能否提交 CR”时走 CR 前复检；否则优先处理用户明确指定的当前联调问题。不要为了覆盖多个模式重复扫描相同材料。

## 仓库知识来源

完整路径先读取仓库根目录的代理说明或知识索引，再按索引读取与本次变更相关的业务规则、工程约定和项目背景。知识目录名称不固定，不得假设所有仓库都有 `spec/knowledge/`，也不得把某个仓库的租户、渠道、金额或业务开关规则强加给其他仓库。

仓库没有显式知识库时，使用当前需求材料、代码、配置和既有工程模式建立有限基线，并明确知识缺口。有限基线至少需要一项变更证据和一项预期依据；当前代码和历史实现只能证明实现现状或先例，不能单独定义业务预期。无法确定预期时将相关场景标记为 `待确认`；若该缺口使必验场景无法设计或判定，联调准备结论为 `暂不可开始联调`，CR 准备度最高为 `PARTIAL`。

## 共享判定规则

- 证据分为代码、命令、文档、人工证据和推测；推测只能标记 `待确认`。
- 只有“预期有明确依据、当前存在可复现不一致、影响正确性/数据/安全/接口契约/必要验收”同时成立时，才能标记 `阻塞`。
- 场景状态只使用：`待联调`、`联调中`、`待确认`、`待复验`、`阻塞`、`已通过`、`不适用`、`本次不处理`。
- 没有实际验证证据不得标记 `已通过`；相关代码、环境或需求变化后，原 `已通过` 场景改为 `待复验`。
- CR 前复检必须分开输出“准备度”和“动作建议”；`PARTIAL` 不等于可正式提交评审，具体动作按 [cr-review.md](references/cr-review.md) 判定。
- 默认在对话中延续场景台账；用户要求保存时才生成 `change-readiness.md`。跨任务没有可读取来源时，请用户提供原记录，不假装拥有永久记忆。

## 失败、重试与停止

| 情况 | 处理 |
|---|---|
| 文件不存在、参数错误、权限不足、仓库范围无法识别 | 不重复尝试；记录缺口并给出一个最小补充动作 |
| 网络超时或工具瞬时失败 | 最多重试 1 次；仍失败则保留已取得证据并说明未完成项 |
| lint、测试、类型检查或构建失败 | 不自动修改代码；记录命令和结果，按影响判断状态 |
| 一次定向追问后仍没有关键证据 | 将场景标为 `待确认` 并停止扩张检查范围 |

## Gotchas

- Skill 被触发不代表要执行完整检查；单个联调问题必须走快速路径。
- 工作区相对 `HEAD` 的 diff 不一定等于整个需求变更。
- 截图只能证明用户可见现象，不能单独证明请求参数或后端状态。
- 上传成功不等于业务保存、异步处理或最终回显成功。
- 代码注释、命名和历史实现不能单独定义本次需求。
- 单个场景不能使用 `READY`；`READY/NOT_READY/PARTIAL` 只用于整个需求的 CR 前复检。

## 边界与软路由

PRD 澄清、技术设计和代码实现不属于本 Skill。若当前平台存在对应能力，可以建议用户切换，但不得将其他 Skill 作为必要依赖；对方不可用时也不能阻断本 Skill 的联调和复检能力。
