# CR 前复检

> 功能：在提交 Code Review 前，结合最新代码、联调台账和验证证据评估整个需求的准备度。与联调准备不同，本模式必须重新核对最新 diff，并输出 `READY/NOT_READY/PARTIAL`。

## 执行流程

1. 读取已有场景台账和联调证据，再按联调准备相同的范围原则重新读取最新 diff。
2. 按 SKILL.md 的仓库知识规则加载相关知识，依据 [checklist.md](checklist.md) 复核业务规则、接口链路、工程约定和提交卫生。
3. 按 checklist.md 的必验规则检查阻塞项是否解决、必验场景是否具备最低证据，以及代码或环境变化是否使旧结论需要复验。
4. 按仓库现有命令执行与变更范围匹配的 lint、测试、类型检查或构建；尊重用户限制，不新增依赖、不编造命令。
5. 运行命令前后核对 Git 状态，保留用户已有改动，不把命令副作用混入结论。

## 准备度

- `READY`：相关静态检查通过；需要联调的场景均有验证证据；没有未解决阻塞。
- `NOT_READY`：存在有明确依据且可复现的业务、工程、接口或联调阻塞。
- `PARTIAL`：范围、知识、命令结果或联调证据不完整，无法完整判断。

需要联调但没有联调证据时最高为 `PARTIAL`。确认不需要后端联调的变更，在静态检查和必要验证通过后可以为 `READY`，并说明依据。

## CR 动作判定

准备度和动作是两个独立结论，必须同时输出：

| 准备度 | 创建 Draft CR | 正式提交评审 | 合并或上线 |
|---|---|---|---|
| `READY` | 允许 | 允许 | 仍需遵守仓库和团队门禁 |
| `PARTIAL` | 允许，但必须显著注明缺失证据 | 默认不允许 | 不允许 |
| `NOT_READY` | 不建议 | 不允许 | 不允许 |

当前平台不区分 Draft 和正式评审时，将“提交 CR”视为正式提交评审。只有仓库或团队明确规则允许，或用户明确授权本次例外时，`PARTIAL` 才可以正式提交；此时动作标记为“例外允许”，保持 `PARTIAL`，并列出授权来源、缺失证据、风险和补验责任。截止时间、已有投入和“以后再补”不能单独改变准备度或动作。

## 输出顺序

1. 检查结论、准备度与动作建议
2. 检查范围、排除项和证据
3. 代码变更摘要
4. 业务与工程风险
5. 联调范围与场景台账
6. 阻塞、待确认和本次不处理项
7. 已执行验证与待补验证
8. CR 前最小下一步
