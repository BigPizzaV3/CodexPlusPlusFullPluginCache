# 実行環境別の動き

## 原則

製品名だけで能力を決めつけず、その会話で実際に使える道具を確認する。同じPluginでも、Chat、Work、Codex、Web、デスクトップ、モバイル、クラウド、接続したパソコンで使える道具が異なる。

## 能力別の経路

| 使える能力 | 実行する内容 |
|---|---|
| Web調査、ファイル、画像生成、利用者のローカル保存先、ブラウザ操作 | 全工程。完成画像をデスクトップの専用フォルダへ保存し、見出し画像の納品時に一度だけ確認を得てnote新規下書きへ登録できる |
| Web調査、ファイル、画像生成、利用者のローカル保存先 | 記事、見出し画像、任意の差し絵まで完成し、画像をデスクトップの専用フォルダへ保存。下書き登録は行わない |
| Web調査、画像生成 | 記事と画像を会話内で完成。文字数や画像寸法は使える手段で検査し、未検査を装わない |
| Web調査のみ | 記事一式まで完成。タイトル選択後はデザイン方向を内部で一つに決め、画像は生成せず、その方向の正確な制作指示を一案だけ返す |
| Web調査なし | 新規記事の調査工程を完了扱いにしない。利用者の一次資料を受け取るか、対応環境で再開する |

## Webとモバイル

Pluginが表示されることと、ローカルのブラウザやファイルへ触れられることは別である。一方、対象プランのChatGPT Workでは、Web、iOS、Androidの会話にクラウドブラウザが提供される場合がある。実行面だけで下書き登録を不可と決めず、現在の会話でnoteを操作できるブラウザ能力が実際にあるかを確認する。クラウドブラウザは利用者のローカルブラウザとは別セッションであり、ローカル側のログイン状態を引き継ぐとは限らない。

file処理が使えることと、利用者から見えるデスクトップへ書き込めることも別である。Webやモバイル等でローカル保存先へ書き込めない場合は、画像を会話内へ表示し、「ローカル環境への保存はできなかったので、こちらの画像を保存して使ってください。」と案内する。

ブラウザ操作が使える場合も、会話開始時には下書き登録の希望を聞かない。完成物が見える状態で「noteの下書き登録まで進めますか？ 公開はしません。」と尋ねる。可否をまだ調べていない場合も、Webやモバイルだから使えないと推測してこの確認を省かない。承認後に手動ログインが必要になっても、登録内容が変わらなければ同じ承認を取り直さない。

承認後は、利用者の明示指定を優先し、なければすでにnoteへログイン済みで操作できるブラウザ面を使う。続いてローカルの内蔵ブラウザ、Chrome連携、クラウドブラウザ、コンピューター操作の順に確認する。同じ条件なら、ログイン状態と生成済み画像へのアクセスを保ちやすいローカルブラウザを優先する。クラウド側ですでにログイン済みなら、未ログインのローカルへ切り替えない。Chromeまたはコンピューター操作で別のウインドウやタブを開く前には、利用者へ一文知らせる。

## 失敗時

後半の能力が失敗しても、完了済みの前半を失敗扱いに戻さない。

- 画像生成に失敗した場合、記事一式は維持する。
- 差し絵に失敗した場合、見出し画像は維持する。
- ブラウザ登録に失敗した場合、記事と画像ファイルは維持する。

原因、維持できた成果物、再開に必要な一手だけを短く伝える。
