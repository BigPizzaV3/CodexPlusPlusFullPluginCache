# Користувацькі поля CRM та реєстрація на курс

Поле належить школі та може використовуватися в CRM і на кількох курсах.
Курс посилається на наявний `fieldId`; його `isRequired` належить лише цьому курсу.
Це не питання форми конструктора та не дані конкретного студента.

| Команда | Призначення |
| --- | --- |
| get_custom_fields | Знайти визначення полів за назвою/типом, прочитати налаштування й revision. |
| create_custom_field | Створити поле CRM школи. До курсу автоматично не додається. |
| update_custom_field | Змінити визначення існуючого поля, зберігаючи його ID і тип. |
| get_course_registration_fields | Прочитати поля реєстрації конкретного курсу та їхню обов’язковість. |
| update_course_registration_fields | Зберегти склад полів та isRequired конкретного курсу. |

## Створення й редагування поля

Спочатку виклич get_custom_fields із коротким `query`. Якщо підходяще поле вже є,
використай його ID. При неоднозначній назві уточни потрібне поле; не вгадуй ID.
Пошук включає приховані поля. Є `type`, `limit` (1–100, стандартно 50) і `offset`;
продовжуй за nextOffset лише коли потрібного поля немає на першій сторінці.

Типи: text, textarea, select, boolean, file-public, file-protected, number,
link, phone, email. Тип існуючого поля змінити не можна — так працює редактор CRM.
Для іншого типу потрібне нове поле за дорученням користувача.

Створення приймає settings.name, settings.type та необов’язкові placeholder,
icon, isVisible. Для select потрібні items: [{text, value}], 1–200 варіантів
з унікальними value. Інші типи не мають items. Обмеження кількості символів
textarea (`max_chars`) ці команди не задають: чинна сутність його не зберігає.

Оновлення використовує fieldId, revision вибраного поля як expectedRevision
і лише запитані settings. Не передавай type. Пропущені поля зберігаються;
null очищає placeholder/icon. Якщо items передані, це повний список варіантів.
Для перейменування варіанта змінюй text, зберігай його value. Не вилучай і не
замінюй збережені value без явного доручення: старі відповіді залишаться в CRM.

Зміна визначення діє всюди, де це поле використовується. Якщо користувач просить
назву/варіанти лише для одного курсу, поясни спільне використання й запропонуй
окреме поле. Не роби глобальне перейменування замість локальної зміни.
isVisible — чинний параметр CRM; він не означає додавання поля до курсу.

## Поля реєстрації на курс

Послідовність: знайти курс → get_course_registration_fields → знайти або створити
потрібні поля CRM → update_course_registration_fields.

Запис приймає повний бажаний fields: [{fieldId, isRequired}] і expectedRevision
зі свіжого читання цього курсу. Збережи всі поля, про які користувач не просив
змін. Нова обов’язковість задається явно відповідно до доручення користувача.
Якщо вона неясна, уточни, чи нове поле обов’язкове.

Для прибирання одного поля вилучи лише його з переліку. fields: [] прибирає всі
додаткові поля реєстрації цього курсу. Сутності CRM та збережені значення контактів
не видаляються. Самі користувацькі поля через плагін видаляти не можна.

Прив’язка не змінює назву, тип чи варіанти поля, публікацію, платність, тарифи,
розклади, матеріали або студентів. Налаштування діють одразу. Режим простої
реєстрації та модерацію змінюй окремо через update_course за дорученням користувача.
Підтримуються курси нової версії.

## Виконання й доступ

Визначення полів вимагають custom_fields:read / custom_fields:write; прив’язки
курсу — courses:read / courses:write. Якщо доступу бракує, поясни необхідність
перепідключити школу з цими дозволами. Не проси ключ у чаті.

Кожному запису дай новий requestId. Після QUEUED/RUNNING або таймаута перевіряй
get_execution; не створюй дублікат з іншим requestId. При CONFLICT прочитай
актуальний стан і повторно застосуй лише погоджену зміну з новим requestId.
Після успіху перечитай поле/курс і перевір результат.
