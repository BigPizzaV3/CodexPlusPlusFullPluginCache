# Prepare actual assets and launch packages

Follow the live execution brief, Distribution Kit and [MCP workflow](mcp-workflow.md). Link each artifact to the audience's real task and the mission event it enables. Destination-specific launch facts must come from current official requirements, not assumptions based on another platform.

## Deliverable patterns

| Work | Concrete deliverable and evidence |
| --- | --- |
| Product descriptions | Finished audience/problem/value/differentiator/limitations copy in the live required variant |
| FAQ or buyer objections | Actual factual answers, pricing/setup/data limits and unresolved claims marked plainly |
| Screenshot/demo | Real workflow evidence with non-sensitive data, caption/transcript, current capability limitations; a specification alone remains a brief |
| Founder introduction | Factual relevant experience, real affiliation, approved headshot/attribution when used |
| Reusable resource/content | Usable body or real artifact reference, instructions, accessible context, source-backed claims and rights |
| Directory/profile | Actual platform/category/handle/copy/metadata, eligibility/fees and precise submission state |
| Launch destination | Exact title/tagline/copy, required assets, review/access instructions, checked requirements/fees, measurement plan and gaps |
| Testimonial/case study | Actual quote/outcome evidence, baseline/window and approved exact quotation/attribution; no synthetic customer proof |

Check relevance, accepted product form, account eligibility, current rules, required assets and actual fees. Include observation/check dates. Product Hunt, app stores, extension marketplaces, developer ecosystems, physical-product markets and beta cohorts have different release/fulfillment requirements. Do not invent eligibility or guarantee review approval. A beta installation, wishlist, star or upvote is not a sale or qualifying mission event unless the founder's definition actually says so.

Prepare materials before requesting any missing external publication/submission/spending authorization. Confirm each intended service/account separately. Prior approval applies only to its named destination/content/assets/account/cost/volume; use it without repetitive confirmation when still valid. A founder's public identity preference or a ready asset does not authorize publication.

## Distribution Kit and action persistence

Read live action field contracts; strategy-specific `content`, `asset`, `listing`, `launch`, audit or repair fields may differ. Save full merged work/notes with current `workRevision`; preserve legacy and concurrent material and verify after conflict-aware saves.

`save_asset_content` accepts reusable text or link content, with current asset `updatedAt` as `expectedUpdatedAt`, and replaces content. For a complete product-description kit, the current format is JSON with `type: "product-descriptions"` and string keys `"50"`, `"150"`, `"300"`; practical word ranges are 40–60, 120–180 and 240–360 respectively. All three are needed for the complete kit asset. Use the live tool description if this contract changes. Unchanged content does not establish new evidence or request an AI review.

Logo and screenshot uploads use the app; this text tool cannot create an image attachment. A generated mockup is not a screenshot of working software. Save an actual artifact reference only if it exists and the task permits saving it. Do not invent hosted URLs or declare image readiness after writing a specification.

## Readiness and outcomes

Return the actual artifact, supported claims/permissions, checked requirements/fees, remaining gaps, observed state and next step. Keep prepared, submitted, published, accepted and measured states distinct. Preparation cannot silently complete the action; ambiguous wrap-up first yields a review summary. Attempt-ending actual-result recording requires explicit recording and completed/failed intent, current tokens and honest `measuredMetrics` under the local MCP reference.
