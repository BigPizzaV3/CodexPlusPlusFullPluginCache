# Review and save a listing

Operation names below identify contracts, not direct conversation tools. Resolve them with `sellapp_find_merchant_tools`; call `sellapp_merchant_read` or `sellapp_merchant_write` using `{ "name": "sellapp_...", "arguments": { ... } }`. Native workspace, account, documentation and media tools remain directly callable. See the merchant operation rules for confirmation and store targeting. After a prepared result, summarize the unsaved proposal and stop. Only the user confirms it in the Merchant workspace; never confirm through a tool or click for them, including with Full Access.

Read [merchant operation rules](../../references/merchant-safety.md) and [exact tool contracts](references/tool-contracts.json). Open the workspace with `sellapp_open_merchant` when the user requests an editor or a persistent editor helps review the proposal. Reuse it when already open; do not call the opener for each read, edit, save or confirmation. Conversation tools return data and reviews without opening another workspace.

Find products with `sellapp_list_products` or `sellapp_search_products`, then inspect the selected product with `sellapp_get_product`. Find variants with `sellapp_list_product_variants` or `sellapp_search_product_variants` and inspect one with `sellapp_get_product_variant`. Use the bounded filters and pagination in the schemas. Identify each result's store. Do not assume a product ID belongs to another store.

Build copy from supplied business facts. For a request such as "create a product for my new ebook about frogs", suggest a title and description based on that topic and collect the missing price/currency and delivery details together. Do not require the user to repeat the request in a separate message to create its variant. Label proposed wording and defaults in the review; do not invent claims, prices or delivery content. Propose `PRIVATE` visibility and, for non-serial variants, zero stock when availability has not been specified. Serial stock follows the supplied inventory count; keep the product private until its availability is explicitly reviewed. An editor draft is unsaved editing state. Do not call it a persisted Sell draft. Preserve Sell's actual visibility values `PUBLIC`, `ON_HOLD`, `HIDDEN`, and `PRIVATE`; do not invent active or archived states.

Read `sellapp_get_permissions` for the explicit store before selecting payment methods. Its merchant result lists enabled gateway choices and usable custom methods by ID and name when current product permission allows it. If exactly one usable payment choice is returned, propose it in the review. If several choices are available and the user has not chosen, include that choice in the same request for missing creation details. Never invent a method ID or enable payment configuration. When selecting `CUSTOM_PAYMENT_METHOD`, send the chosen `custom_payment_method_ids` together with `payment_methods`. Preserve both omitted selections during unrelated variant edits.

Before persistence, show the store, product, variants, price with currency and units, delivery, stock, payment methods and visibility. For a new standard offer, use `sellapp_create_product` with its initial variant in `body.variants`. Collect required details before preparing, then let the user review and confirm that one combined request in the workspace: the backend saves the product and variants atomically. Do not create an empty product and stop to ask the merchant to request a variant separately. Use `sellapp_create_product_variant` to add another variant to an existing product, or create a product without variants only when the user specifically wants an empty listing. Inspect the saved product and variant IDs. Use the delivery and product type that matches the merchant’s request. Do not invent serial codes, delivery endpoints, license constraints or recurring billing settings.

For static-value delivery, including a merchant-supplied link, use `deliverable.types: ["MANUAL"]` and put the exact text or URL in `deliverable.data.comment`. The UI calls this **Static Value**. `deliverable.data.stock` is an integer or `null` for unlimited; show the proposed value before approval. Do not send a `STATIC` type or invent `static_value`, `value` or `url` fields. For "create an ebook about frogs for $5 and add a static value pointing to openai.com", propose a frog ebook title/description, clarify the currency if unavailable from context, and use `https://openai.com` as the delivery comment. For USD, the variant pricing is `{"humble":false,"price":{"price":500,"currency":"USD"}}`. Include the enabled payment-method choice and proposed visibility/stock in the same combined review. Each initial variant requires `title`, `description`, `deliverable`, `pricing` and `payment_methods`. Include `minimum_purchase_quantity: 1` unless the merchant supplied another valid minimum; show any proposed maximum quantity in the review.

Use `sellapp_update_product` for product fields and visibility. Use `sellapp_update_product_variant` for supported variant fields, and `sellapp_update_product_variant_pricing` for the dedicated pricing contract. Read the current variant before changing price, retain omitted settings, and carry its concurrency token. Pricing amounts use the units declared by the contract; for integer USD minor-unit prices, `1999` is USD 19.99. Preserve currency and any explicit USD-denominated fields. Do not apply coupon major-unit rules to variant pricing. Subscription pricing and cadence use the shared pricing boundary. Fetch enabled subscription payment methods from sellapp_get_permissions. New products may include a SUBSCRIPTION initial variant with frequency, compare-at price and quantity settings; use only an enabled subscription gateway. Existing active plan terms are immutable: report the server denial, keep other supported edits available, and never bypass it. Product settings include receipt notes, section, video, SEO, FAQ and checkout field definitions. Omitted settings and delivery inventory are preserved. The workspace reviews managed-file options and deletion separately; folder tree deletion, duplicate/draft/reorder actions and community provisioning remain dashboard workflows.

Use `sellapp_delete_product` or `sellapp_delete_product_variant` only for the exact reviewed store and record. Show the existing product/variant and deletion consequence, carry each supported `expected_updated_at`, prepare, then let the user review and confirm in the workspace. Never describe prepared deletion as complete.

For bulk product edits, use `sellapp_batch_update_products`, with at most 50 products per user action. Read each affected product first. Show every record and proposed field change, include supported per-record snapshots, prepare, then let the user confirm the identical request in the workspace. Preserve the response's atomic or partial-result behavior and inspect failures separately. Do not use batch creation or batch deletion in this release.

After every completed save, reload through the matching get tool and show the persisted values, including whether the product is public or hidden. If panel and conversation changes disagree, resolve the current unsaved proposal before saving. A stale result must not overwrite newer editor changes.

## Serial inventory, license keys and other deliverables

Standard variants may combine `DOWNLOADABLE`, `TEXT`, `MANUAL`, `DYNAMIC` and `LICENSE_KEY`. Read `sellapp_get_product_variant` and `sellapp_get_variant_deliverable_configuration` before changing an existing variant. Preserve unedited configuration and inventory; send `expected_updated_at` from the fresh read for variant or configuration edits.

For merchant-supplied unique codes use `deliverable.types: ["TEXT"]`, `deliverable.data.serials` as an array of exact supplied strings, `removeDuplicate` and `parsingMode`. Each purchase consumes inventory; do not set an unrelated stock count. A literal code `"1"` is a serial value. An existing serial record ID identifies inventory belonging to one variant; do not invent an ID, copy, move or replace another variant’s code. Clarify an ambiguous request for “serial id 1” before using it. Include the initial TEXT variant in `sellapp_create_product` through `body.variants` for one atomic creation.

Use `sellapp_list_variant_serial_inventory` to read inventory IDs and counts. Unsold code values are available only in private host metadata for the authorized editor and do not belong in model context. `sellapp_append_variant_serial_inventory` adds exact supplied codes; `sellapp_delete_variant_serial` removes the selected unsold record. `sellapp_replace_variant_serial_inventory`, or a variant update containing `data.serials`, replaces all unsold codes. Show the replacement count and current inventory count before approval. Sold codes are retained. A changed inventory invalidates the reviewed replacement; reload and prepare again.

For generated keys to a SaaS or desktop app use `LICENSE_KEY`. Collect expiration and activation choices together: `isLicenseLengthUnlimited` and `isLicenseLimitUnlimited` are explicit booleans; a finite expiration also requires `licenseLength` (1–1000) and `licenseLengthUnit` (`DAY`, `MONTH`, `YEAR`); a finite activation limit requires `licenseLimit` (1–1000000). `licensePrefix` is optional, at most 10 letters, numbers or hyphens. Include these settings in the initial variant for atomic creation. Generated keys and merchant-supplied key inventory are different choices; ask when the intent is unclear. Configuration can be read and edited; customer-issued keys stay redacted.

For dynamic delivery use `DYNAMIC` with the merchant’s public HTTPS `data.webhook`. The backend validates the URL. The configured endpoint stays in private editor metadata; preserve it when unchanged. Use `sellapp_replace_variant_deliverable_configuration` to edit managed static, webhook, license or downloadable configuration while retaining types managed by other resources. Removing Downloadable delivery also removes its managed files and folders; make that removal explicit in review.

Bookings use a `booking` product with only `BOOKING` delivery. Use `sellapp_get_booking_configuration`, `sellapp_list_booking_availability` and `sellapp_update_booking_configuration` for the selected variant; retain connected-provider settings not explicitly edited. Bundles use a `bundle` product with only `BUNDLE` delivery: inspect `sellapp_list_bundle_items` and `sellapp_get_bundle_item`, then review `sellapp_attach_bundle_items` or `sellapp_detach_bundle_items` with exact current-store variant IDs and quantities. Credits use their owning product resource: `sellapp_list_credits_products`, `sellapp_search_credits_products`, `sellapp_get_credits_product`, `sellapp_create_credits_product`, `sellapp_update_credits_product` and `sellapp_delete_credits_product`. Do not mix these exclusive deliverables into a standard product. Keep wallet/customer balance adjustments outside this plugin’s supported conversation actions.

## Product images

Use `sellapp_prepare_product_image_upload` for a ticket bound to the connection, actor, store, and existing product. The user selects the image in the merchant app. Send binary data only through the ticket's dedicated HTTP upload route; never put bytes or base64 in MCP arguments. JPEG, PNG, GIF, and WebP are supported, up to 10 MiB per image and four product images in total. Tickets expire after ten minutes.

After a successful staged upload, use `sellapp_attach_product_image` with the current product snapshot and the validated upload reference. Follow its existing prepare/confirm contract. Show that attachment appends to the existing image list. Report success only after the backend confirms attachment and the reloaded product retains its prior images. On failure, keep the existing product and report a retryable staged upload only when the backend says it remains usable. Do not fetch an arbitrary image URL.

To replace an image, carry its `image_id` from a fresh product read as `replace_image_id` when preparing the upload and when reviewing attachment. The replacement retains its position and can be prepared at the four-image limit. Show the image being replaced and the staged replacement before approval.

Use `sellapp_manage_product_images` to remove or reorder images. Send the complete ordered list of current `image_ids`; omitted images are removed, an empty list removes all, and the first image becomes the cover. Present removals and final order, prepare, then let the user review and confirm in the workspace the identical request. Reload afterward. Never invent an image ID or use a private storage path as an ID.

## Digital delivery readiness

Use `sellapp_get_variant_delivery` for the explicit store, product, and variant to inspect bounded file metadata and delivery readiness. Keep product visibility separate from attached-file readiness. A metadata result is not proof that checkout or a customer download succeeded. Never expose private paths, signed customer download URLs or customer-issued license keys. Merchant-supplied static delivery text may appear in a reviewed change; raw unsold serial codes and private webhook endpoints stay in the authorized editor.

To start a new download offer, create a HIDDEN or PRIVATE standard product, then review `sellapp_create_download_variant` with its fresh product snapshot and merchant-supplied title, single-payment price and payment methods. This native action creates an empty DOWNLOADABLE variant at zero stock without manual instructions. Ordinary REST creation still requires inline downloadable files. Stage and review a private delivery file, inspect storage readiness, then separately review inventory and visibility. Existing eligible MANUAL-only zero-stock variants can use `sellapp_setup_variant_downloads`; review removal of their manual instructions. Never silently alter availability or invent placeholder instructions.

For an existing variant with DOWNLOADABLE selected, use `sellapp_prepare_variant_delivery_upload` with fresh product and variant snapshots. The merchant selects a nonempty file up to 10 MiB in the app. Transfer bytes only through the private multipart upload route; do not put bytes or base64 into tool arguments. The ten-minute ticket supports cancellation through DELETE on its signed upload URL. This plugin limit is smaller than the dashboard limit.

Use `sellapp_attach_variant_delivery_file` to review and confirm attachment. Show the store, product, variant, filename and size, and explain that customers with access to the variant may receive the new file. Existing files and visibility stay unchanged. The new file uses purchase-IP restriction and no download-count limit. A completed attachment may still have pending storage; reload delivery details and distinguish available bytes from pending or unavailable storage. Do not publish the product as part of uploading a file.

## Product mentions

Use `sellapp_search_product_mentions` with `{query}` for the desktop's product typeahead. Returned resource links identify their store. Resolve the resource through `resources/read` and open its product in the merchant workspace. Revalidation controls membership, installation, reference expiry, store, and record. If the reference fails, explain the failure and search again; never reuse the record under another store.

## Import public files

Use `sellapp_import_product_image` or `sellapp_import_variant_delivery_file` with a current explicit store/product/variant snapshot and public HTTPS file link. Supported public Dropbox shared-file links and compatible public Google Drive file links are normalized; private provider accounts, folders and sign-in screens are unavailable. Files are bounded to 10 MiB, HTTPS redirects are revalidated, and image formats retain normal validation. Import only stages a ten-minute upload ticket. Review and confirm the existing attachment tool separately. Discarding an import cancels the returned staging URL; late results are discarded and cleaned up. Keep source credentials and provider tokens out of arguments. Live provider compatibility has not been verified for this release.
