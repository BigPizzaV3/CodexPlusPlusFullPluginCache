# Friendly selections and checkout actions

Keep choices easy to answer and avoid repeating information the shopper already supplied. These are presentation instructions, not new catalog, cart, or payment tools. In ChatGPT, use its **native rich-response controls** for shopping choices and navigation actions when supported. The intended result is actual selectable radio inputs and an actual full-width button, not a prose list or bold Markdown link. Native rich-response controls do not require a separate question tool or an MCP App iframe.

## Product images and source boundaries

Use one primary product image per recommended product; additional gallery images are optional. When the shopper's chosen color is known and preview_product_selection returns a matching productEntityId/variantSKU with a usable selectedImage, use that exact URL. If the color is unknown, the matching image is absent, or the preview cannot be obtained, use the first usable image already returned for the same product by get_product_details (images) or search_products (imageUrl). A standard fallback is a product photo, not evidence that the chosen color is pictured. Never withhold an available standard product photo just because a color preview is missing.

Show the image beside the product/selection summary, using a supported direct-URL image in the native response or Markdown image. A tool call alone does not prove its gallery was displayed. If the host already visibly displays the correct image through the tool gallery, do not duplicate it; otherwise include the exact returned URL in the response's image element. Do not rely solely on an earlier message's gallery. Do not use async_image, image search, generated media, marketplace photos, or guessed URLs. Omit media only if there is no usable returned image or the host refuses every supported direct display. Keep shopping choices and actions usable either way.

Reuse verified image URLs and product details when sufficient. Refresh details only for missing/stale/contradictory information, a new product/option or required price verification. A photo-only correction must not call cart or checkout-creation tools.

## Radio-style choices

Apply this on the FIRST question that offers known body-style, trim, color, or required product-option alternatives. The customer must not need to ask for an interactive selector. Include a labeled radio group and an explicit Continue/submit action in that same response. Keep a Not sure/free-text path for trim. Do not infer that controls are unavailable merely because an earlier response used prose, no separate question tool was listed, or this plugin has no dedicated selector component. Check the actual host response capabilities and use the supported native rich-response format when available. If neither supported native controls nor a supported inline interactive surface is available, state that limitation briefly and accept a text answer; do not claim a selector was rendered.

When asking for body style, film color, required product choices, or known trim alternatives, **render a native rich-response form with radio groups**. Put each independent choice in its own labeled group, such as Headlight color and Fog light color. Include a clear submit/continue action that conveys the selected values back to the conversation. Merely changing a radio value is not a cart mutation. Do not require the shopper to type each answer when interactive controls are supported. Keep a free-text/other or "Not sure" path when supported, especially for trim. Never treat a default selection as a customer-confirmed answer. If a separate native question tool is offered instead of rich-response controls, use that as the next option; absence of that tool alone does not mean rich-response radios are unavailable.

Body-style controls are conditional, not a standard intake field. Use them only after actual fitment for the requested product/coverage establishes an unresolved body-dependent restriction or split. Do not ask cab/body merely because the vehicle has multiple manufacturer configurations or because another product category differs. One verified kit covering the remaining configurations means no body question. Keep normal trim intake; if trim was already answered, retain it. For a real body-dependent split, use a separate Body style radio group with only valid alternatives and Not sure/free text, before claiming one body-specific kit is the match. Shared trim names, result order, a guessed market, a prior assistant recommendation, and a default radio value do not resolve that split. If body is Not sure, compare documented candidates without claiming one is confirmed compatible.

For a merely omitted trim, offer choices only when confidently known for the exact year/make/model and relevant market from the conversation, authorized memory, or reliable vehicle knowledge already available. These choices clarify the vehicle; they do not establish product fitment. Do not invent trims or silently choose one. If choices are uncertain, ask a concise text question once. If the customer says "not sure," "no separate trim," or asks to proceed without it, search and compare the best one or two precuts using documented Fits sections before asking any further trim/configuration question. Strong recognizable clues can identify a likely or clear trim as described in SKILL.md; preserve uncertainty where appropriate.

For colors and product options, first read live MCP product details after vehicle intake is resolved, including an explicitly unknown/no-separate-trim state. Offer the selected product's actual available values, preserving separate groups such as Headlight Color and Fog Light Color. Do not use a universal hardcoded color list or offer a color merely because another product has it. Include every viable value, using additional questions if the host limits choices. Respect earlier choices; only ask for unresolved fields. Follow SKILL.md for fog-light inclusion and the once-only optional protection-plan offer. If the product offers fog-light color selection, present that color group as part of the included kit; do not add a missing-contents warning. If a protection plan is actually available, offer it once with its verified name and price, using an optional, initially unanswered selection. Do not add it without explicit consent. A skipped/default/unoffered plan is not a declined plan: omit it from the confirmed-selection summary and do not say the shopper chose to leave it off.

Selecting a color or trim supplies a preference. It is not by itself permission to add a product, change quantity, or purchase. When the shopper already asked to add the kit and selection completes the required information, carry out that authorized add without another redundant confirmation.

Treat typed or spoken trim, color, quantity, and coverage choices exactly like submitted selector values. Resolve clear customer wording to the live option labels without making them click the same choices again. Ask only about a genuinely unresolved or ambiguous value. A typed or spoken request to add the specified item authorizes that cart action under the same rules as the UI; selecting preferences alone does not. Update or summarize the chosen values rather than re-presenting an empty required form. Preserve the documented modifier/checkout fallback and never claim website selections transferred without verification.

Use the actual response-format capabilities supplied by the host; do not invent a rich-response schema or tool name. Normal Chat and Work can expose different presentation capabilities. If native rich-response controls are absent but a supported inline interactive-HTML/visualization surface is available, use it with real radio inputs and an explicit send-to-chat action; follow that host's visualization guidance. Use its supported follow-up-message bridge with the selected values, never direct cart/API calls from the form. No customer credentials belong in presentation state. If neither interactive surface is available, show a compact labeled list and accept a text reply, stating the limitation briefly. Do not draw fake clickable radio circles or claim controls were rendered. Do not reopen the failed experimental account invitation component for product selections.

## Product-page selection summary

After a guest configuration/price/photo confirmation with no cart authorization, still render the full-width **Choose options on Lamin-x** action using the verified selected-variant product page. Put the known choices/quantity and any verified optional-plan charge beside it. Do not call cart or create_checkout_url tools, label the product page checkout, or treat interest in a paid plan as consent. This is a useful read-only next step, not a failed checkout. An ordinary inline product link is not the intended primary action. For a connected shopper without an existing checkoutURL, render an **Add to cart** action that submits the cart request back to the conversation; never send the account to a product page as its checkout or mutate before submission. Explicit photo-only correction requests preserve their existing no-cart/no-checkout behavior. Use the supported native primary-action format first, then the documented interactive/link fallbacks below if unavailable.

Read the optional plan's matching catalogFitment.checkboxLabels entry before saying its price is unknown: the public label can include the surcharge that checked/unchecked values omit. Use actual returned labels, never a fixed plan amount or presumed consent. Preserve account variant pricing and normal guest/dealer checkout routing.

Choose the guest action using the actual checkout result and verified cart configuration, not a product category, kit name, fog-light assumption, or color-choice heuristic. A variant-only color selection can use the returned checkout link when its SKU carries the full configuration. On an actual checkout error or a link that cannot carry a verified modifier, place the customer's confirmed option labels/values and quantity immediately beside the **Choose options on Lamin-x** action. Use preview_product_selection's exact productPageURL for the verified selected variant when available. Only its matching preselectedOptions may be described as already selected; confirm remaining modifiers (including separate fog colors) and quantity on the website before adding there. If unavailable, use the unmodified verified product page and ask the shopper to select all listed values. Never invent option URL parameters or claim all fields transferred. Accept typed, spoken, and selector choices equally. For a verified native checkout link that fully represents the items without unsupported modifiers, use the checkout action below instead.

## Connected-account action boundary

An active account uses the exact configured-cart checkoutURL, including modifiers. preview_product_selection supplies media and an optional product-page link only; its productPageURL never replaces verified dealer checkout. For a photo/price-only request without an existing verified checkout link, show the summary and an Add to cart next step when useful, not a product-page action presented as the dealer checkout. A later explicit checkout request permits its normal configured-cart workflow. A guest keeps the documented native link/product-page fallback. Actual account API failures must be explained rather than silently switching to guest behavior.

## Prominent checkout action

After a verified cart addition, provide a concise item/selection/quantity/price summary and offer the checkout handoff when appropriate. A shopper can still continue shopping; do not force checkout after every add.

Follow checkout-handoff.md before presenting any action. If a tool-returned link supports the requested cart configuration, **render a native rich-response primary, full-width link/action button** labeled **Continue to Lamin-x checkout**, optionally with the verified subtotal directly above it. It must open the exact returned Lamin-x URL, using the host's supported external-navigation action. Do not open or follow it automatically. Keep it prominent and separate from surrounding prose. Include a normal clickable link as an accessible fallback if necessary. Do not fabricate button syntax or create a homemade checkout URL. A separate button-rendering tool is not a prerequisite when native rich responses already support buttons.

If native rich-response buttons are absent but a supported inline HTML/visualization surface is available, render a full-width primary anchor using the verified URL and that surface's supported external-link handling. If neither surface supports it, use a standalone bold Markdown link labeled **Continue to Lamin-x checkout**, acknowledging that this is a link fallback. Do not silently choose Markdown just because no separate button tool exists.

When the native checkout URL cannot preserve requested modifiers, **still render a prominent full-width button** labeled **Choose options on Lamin-x**, pointing to the verified official product page. Give one short, practical next step identifying the options and quantity to choose there. Do not describe checkout as broken or explain the internal integration during an ordinary handoff. The customer must understand what to do on the website; describe only preview_product_selection's verified matching preselectedOptions as selected, and never call this product-page destination a cart. For a kit with multiple pieces, use: "Since there are multiple pieces to this kit, please confirm your choices on the product page to continue." Otherwise use: "Please confirm your choices on the product page to continue." Put the confirmed selections and quantity beside the action. An expected checkout-link error such as INVALID_ARGUMENT uses this same normal handoff; do not mention the error code, checkout-link service, or inability to generate a direct link. Separately explain actual failed/uncertain cart mutations or missing fallback destinations in plain language, and give technical details only if explicitly requested.

Customers complete checkout and enter payment on Lamin-x themselves. Opening the link is their choice; do not open a cart-rebuilding checkout URL merely to test the button.
