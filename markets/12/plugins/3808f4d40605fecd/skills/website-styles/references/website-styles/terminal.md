## Purpose

Create a precise, text-led website shaped by the clarity, sequence, and input–response logic of a computer terminal.

Terminal is an interface-derived treatment with a complete default foundation, not a dark preset, retro simulation, developer archetype, or command-line replacement for ordinary navigation. Its identity comes from ordered text, prompt–response relationships, character-grid discipline, visible context, and functional economy within a conventional accessible website.

After the shared chat confirmation, use this profile only when Terminal was selected under confirmed delegation or preserved from the confirmed restatement. Apply it with the relevant Design intent skills and canonical Alpy package.

This profile defines semantic relationships and selection priorities. It does not define CSS, raw values, named typefaces, fixed colors, components, tokens, modes, breakpoints, commands, product behavior, effects, or canonical interaction behavior.

## Classification

- **Default foundation:** A complete text-led foundation with canonical structure, explicit context–input–response relationships, character-grid discipline, restrained surfaces, accurate technical content, conventional components and states, and quiet functional regions. No second style selection is required.
- **Best suited for:** Developer tools, infrastructure, software, open-source projects, documentation, security, data services, technical portfolios, engineering organizations, digital studios, games, experimental publishing, and brands genuinely related to computing or systems.
- **Use selectively for:** Broad consumer audiences, long editorial reading, emotional storytelling, hospitality, care services, young audiences, unfamiliar technology, high-consequence tasks, and content with little authentic technical relationship.
- **Compatible with:** None declared until adjacent profiles have been researched and cross-style validation confirms a coherent combination.
- **Conflicts with:** None declared until adjacent profiles have been researched and cross-style validation confirms a material conflict. Do not infer either relationship.

Terminal does not establish that a visitor is technical, that a command is valid or safe, that output is live, that a system is connected, or that the website provides terminal access. Treat commands, logs, status, permissions, and system behavior as product truth.

## Identity

### Principle

Make the system legible through ordered text, explicit context, and clear response.

### Character

Terminal should feel:

- Precise without becoming cold.
- Efficient without hiding explanation.
- Dense only when the information requires it.
- Direct without becoming cryptic.
- Confident without pretending to have system authority.

### Signature traits

Build the treatment through:

- A stable canonical grid influenced by character-cell alignment and line-based reading.
- Clear distinctions among context, prompt, input, output, metadata, status, and explanation.
- Sequential content flow that makes cause, response, and next action easy to follow.
- A canonical code or monospaced role in terminal-derived regions when the package provides one.
- Restrained surfaces, decoration, and imagery so information remains primary.
- Consistent textual markers, labels, prefixes, dividers, and grouping with real meaning.
- Accurate command, code, log, and system content rather than decorative technical filler.
- Conventional navigation, controls, forms, focus, validation, and recovery.

The result must remain recognizably Terminal without dark mode, black, green, amber, neon, a prompt glyph, monospaced body copy, window chrome, scanlines, pixel effects, a blinking cursor, typing animation, code rain, or hacker imagery.

### Anti-goals

Do not reduce Terminal to:

- Bright green or amber text on a black field.
- A monospaced font applied to every word.
- A fake terminal window around every section.
- Prompt symbols, brackets, pipes, slashes, underscores, file paths, or code used as decoration.
- Scanlines, glow, noise, flicker, automated typing, blinking cursors, or endlessly updating logs.
- Hacker, cybersecurity, command-center, or science-fiction imagery without confirmed relevance.
- Navigation that requires people to remember or type commands.
- Buttons and links disguised as shell input.
- Fabricated commands, logs, output, status, metrics, timestamps, hosts, paths, users, or errors.

## Expression Model

Infer one dominant emphasis from the confirmed purpose, content, audience, and functionality. Combine emphases only when each has a distinct responsibility. Do not ask the user to configure a Terminal subtype.

- **Command and response:** Organize authoritative or clearly illustrative technical content as context, command, result, and next step. Keep input and output distinct, explain the command, and never make decorative phrases appear runnable or replace ordinary website actions with syntax.
- **System and status:** Use confirmed events, logs, health, progress, environment, or system context to prioritize current condition, exceptions, source, time, and available action. Never imply that decorative output is live, complete, or authoritative.
- **Documentation and learning:** Lead from explanation to runnable example, expected result, verification, troubleshooting, and reference. Keep terminology, placeholders, prerequisites, versions, platforms, and outcomes explicit.
- **Product and capability:** Use concise terminal-derived regions to demonstrate a confirmed capability while ordinary language explains value, evidence, use cases, limitations, and next steps.
- **Editorial and identity:** Use line-based hierarchy, concise labels, metadata, controlled type, and sequential reveal for brands or cultural work with an authentic computing relationship without pretending content is executable.

### Functional restraint

Use unchanged canonical task presentation for checkout, consent, authentication, permissions, personal data, legal, medical, financial, security, deletion, recovery, and other consequential actions. Keep Terminal notation outside the control, label, help, error, action, and confirmation grouping.

State the affected object or data, amount or scope, recipient, consequence, and permanence when applicable. Preserve canonical review, correction, confirmation, cancellation, recovery, and completion feedback. Missing required protection blocks the affected flow; Terminal never supplies a substitute.

For copied commands, prefer authoritative read-only, preview, dry-run, scoped, non-production, and reversible examples when available; never invent a safer flag or environment.

### Minimum signature

A recognizable Terminal direction requires:

- A stable canonical website structure and conventional interaction model.
- An authentic `context → input → response` or `context → status → next action` relationship; an isolated decorative code block is insufficient.
- At least two visibly distinct semantic channels: input, output, context, metadata, status, or explanation.
- Line-based sequential rhythm, disciplined alignment, restrained ornament, and a subtle alignment echo beyond the primary region.
- A canonical code or monospaced role for authentic commands and output when available.
- Accurate technical content and unambiguous actions, states, and focus.

Use the nearest supported Terminal expression only when this signature, confirmed meaning, familiar interaction, and accessibility survive. Otherwise report the missing coverage instead of introducing a typeface, component, command convention, or local terminal effect.

### Website and Product Design boundary

Use Terminal for public marketing, documentation, education, portfolios, launches, technical evidence, open-source projects, product explanation, and bounded canonical demonstrations.

Product Design, when available, owns command entry, shells, terminal emulators, REPLs, authenticated consoles, live logs, sessions, history, permissions, secrets, remote connections, and operational workflows. Otherwise keep the work within confirmed public scope and report unresolved product behavior.

Terminal may shape confirmed structure and expression. It cannot introduce executable commands, command languages, environments, privileges, connections, live output, operational state, security boundaries, keyboard models, or product behavior.

### Distinction from adjacent directions

- **From Modern Dark:** Modern Dark is organized through mapped dark surfaces, restrained light, depth, and contemporary focal moments. Terminal may be light or dark and is defined by textual sequence and input–response logic.
- **From Cyberpunk:** Cyberpunk expresses tension among technology, people, power, place, and consequence. Terminal does not imply dystopia, surveillance, augmentation, neon, urban decay, or high-tech–low-life narrative.
- **From Retro:** Retro deliberately references a historical period or visual language. Terminal may use contemporary terminal conventions without nostalgia or vintage hardware cues.
- **From Monochrome:** Monochrome is a restricted color treatment. Terminal can use a complete canonical color system when content and state require it.
- **From Neo Brutalism:** Neo Brutalism uses exposed structure, forceful boundaries, and deliberate rawness. Terminal uses ordered textual channels and response logic without roughening the interface.
- **From Bold Typography:** Bold Typography uses type as the dominant expressive medium. Terminal uses typographic roles as an information protocol rather than spectacle.
- **From a real command-line interface:** This profile controls website expression. It does not define a shell, terminal emulator, command language, execution environment, keyboard model, or security boundary.

These distinctions do not make adjacent profiles available, compatible, or conflicting. Do not load or combine another profile without validated support through the style-selection contract.

## Visual Expression

### Hierarchy

Begin with the confirmed visitor outcome. Use canonical typography, spacing, placement, line sequence, grouping, and semantic emphasis to establish a clear path from context to action or response.

Let one terminal-derived region lead at a time. Within it, distinguish the active or primary line from supporting metadata and prior output without making every token, label, and status equally prominent.

Do not use technical density as a substitute for hierarchy or credibility.

### Typography character

Use only typefaces, typography roles, complete tuples, and mappings available in `alpy/type-scale.md`. Resolve component-owned typography slots and bindings through `alpy/component-tokens.md`.

Use a canonical code or monospaced role for authentic commands, code, paths, identifiers, logs, output, and terminal-derived display regions when available. Preserve canonical body, heading, label, and action roles wherever they improve reading, orientation, or inclusion.

Monospaced text reflects character-cell alignment and code semantics; it is not required for every heading, paragraph, navigation item, or control. Validate legibility, language coverage, weight, spacing, punctuation, ambiguous characters, and text expansion.

Do not introduce a terminal, bitmap, pixel, OCR, segmented, monospaced, or technical typeface locally. Do not use arbitrary tracking, all-uppercase text, reduced size, or dense line spacing to force the aesthetic.

### Color behavior

Resolve component-owned color through `alpy/component-tokens.md` and remaining intent through `alpy/semantic-tokens.md` and explicit mode mappings.

Use foreground, background, surface, border, text, icon, brand, and emphasis roles to establish terminal regions and textual hierarchy. Reserve functional roles for focus, status, validation, selection, and consequence.

Terminal may be light, dark, monochrome, restrained, or colorful. Modern terminal software supports configurable profiles and multiple schemes; no historical palette is mandatory.

Do not default to green, amber, cyan, black, gray, or luminous text. Do not use color alone to distinguish command, output, error, success, warning, active process, placeholder, or copied state.

### Character, line, and marker behavior

Use punctuation, prefixes, labels, dividers, line numbers, prompt marks, and textual indicators only when they have a stable, documented meaning. Pair symbolic distinctions with structure and text when needed.

Keep prompt characters outside copied commands when the component and workflow support that distinction. Treat pipes, brackets, braces, flags, paths, and placeholders as syntax only when they are accurate.

Do not scatter command characters or ASCII-like decoration across unrelated content. Do not build logos, illustrations, borders, charts, or icons from text characters unless supplied and approved as assets.

### Shape, surface, and depth

Use canonical components, radii, borders, surfaces, depth, and anatomy to communicate grouping, hierarchy, state, and interaction.

Favor economical containment and explicit boundaries. A terminal-derived region may use a canonical code, panel, inset, or grouped surface when available; the entire website does not need to resemble a terminal window.

Do not add title bars, traffic-light controls, tabs, beveled frames, hard corners, inset borders, or window shadows unless canonical capability and content purpose require them.

### Imagery and media

Use only supplied and approved photography, interface captures, diagrams, product media, video, and brand assets.

Favor authentic product output, hardware, work, people, systems, environments, or results when they clarify value and context. Terminal screenshots must be readable, current, permissioned, and accompanied by meaningful alternatives.

Do not invent screens, system access, code, dashboards, server rooms, threat maps, logs, or developer environments. Do not use code rain or generic command-line imagery as proof of technical capability.

### Iconography and technical symbols

Use only canonical Alpy icons, sizes, roles, and component bindings for controls and system meaning.

Keep shell symbols, status markers, prompt characters, keyboard notation, and decorative glyphs distinct from interactive icons. Label unfamiliar symbols and preserve text alternatives.

Do not substitute text characters for canonical icons or recreate icons as pixel, ASCII, or terminal glyphs.

## Context, Input, Response, And Status Grammar

Use five relationships to translate Terminal across the whole website:

- **Context:** Establish the task, environment, source, scope, or subject before technical detail.
- **Input:** Present confirmed commands, choices, or requests distinctly and only when they are real or clearly illustrative.
- **Response:** Show the accurate result, explanation, evidence, or next step associated with the input.
- **Status:** Distinguish current, historical, expected, simulated, partial, unavailable, success, warning, and error meaning explicitly.
- **Rest:** Give reading, navigation, forms, and consequential tasks enough quiet to remain conventional and clear.

These are reasoning aids, not new syntax, commands, components, tokens, states, data, or behavior.

## Spatial Expression

### Layout bias

Preserve the primary layout, hierarchy, density, and any deliberate supporting treatment in the confirmed direction. Any suitable primary layout may support Terminal when its documented purpose fits.

Apply `Editorial`, `Asymmetric`, or `Immersive` only when the confirmed direction calls for it. Character-grid influence, command–response sequence, dense output, or console-like grouping does not independently select another composition or treatment.

Use one dominant composition per page or route family. Terminal does not independently choose the layout or require a full-screen console.

### Grid and alignment

Use exact containers, columns, spans, gutters, and responsive behavior only through Grid and Layout and explicit canonical package support.

Favor stable vertical edges, repeatable line relationships, aligned metadata, clear indentation, and predictable region boundaries. Use character-grid influence as a compositional principle, not a fixed measurement system.

Do not force all content into equal-width cells, narrow terminal columns, rigid tables, or simulated terminal rows.

### Rhythm and density

Build rhythm through sequences of context, statement, response, explanation, and action. Use pauses between dense terminal-derived regions so visitors can orient and understand the larger message.

Preserve the confirmed density. Compactness may support authentic logs, code, or system data, but it is not a default for marketing, reading, navigation, or forms.

Do not fill every viewport with continuous lines, metadata, badges, or output.

### Content measure and flow

Keep prose, commands, code, paths, logs, output, tables, annotations, and metadata readable at their intended width. Wrap explanatory text normally and preserve command meaning through supported wrapping, continuation, scrolling, or restructuring.

Do not clip important output, rely on horizontal scrolling for ordinary page content, or shrink type to preserve a desktop terminal composition.

## Command, Output, And System Integrity

### Commands and examples

Use only commands established by an authoritative project source. Preserve version, platform, environment, privilege, prerequisites, expected result, and consequences when material; report missing truth instead of treating testing alone as authority or safety.

Keep copyable content free from prompts, annotations, line numbers, and incompatible optional syntax. Do not offer secrets, destructive commands, or unreviewed values as routine copy targets. When authoritative content requires a destructive command, preserve its exact scope, prerequisites, consequence, confirmation, and recovery; never invent them.

### Input and output

Separate input from output when both appear. Label expected, illustrative, partial, variable, redacted, or live output accurately. Show output only when it helps people verify, understand, or continue.

Do not edit output in ways that imply a different result. Mark omissions and variability according to the applicable documentation guidance.

### Prompts, paths, and environment

Use a prompt or environment indicator only when it helps distinguish user, host, local or remote context, privilege, path, or execution state. Explain unfamiliar context and never imply elevated access casually.

Do not expose private usernames, hostnames, directories, tokens, keys, customer data, internal endpoints, or environment details.

### Logs, events, and status

Present source, time, severity, scope, persistence, and current relevance when confirmed and useful. Keep persistent records distinct from transient notifications and historical output distinct from live state.

Do not fabricate log volume, uptime, incident history, progress, security events, system health, or performance.

### Plain-language support

Present purpose, prerequisites, environment, step, expected result, verification, recovery, and next action in order when applicable. Explain technical meaning before requiring syntax knowledge and link to full reference.

Do not make visitors decode jokes, abbreviations, flags, file paths, or output to understand the product proposition or primary action.

## Interaction Expression

### [Motion](../ui-design/motion-transition.md)

Static is the default. Selecting Terminal never authorizes new motion, sound, or haptics. Canonically supported motion may explain execution, transition, progress, or change only when the confirmed experience requires it; Terminal must remain recognizable and complete when static.

Do not add automatic typing, blinking text, cursor loops, scanlines, flicker, code rain, scrolling output, loading dots, or repeated text replacement merely to establish the style.

Use only controls and reduced-motion behavior documented by canonical support and applicable confirmed requirements. Remove unsupported moving, blinking, scrolling, or auto-updating behavior and preserve equivalent static meaning.

### Keyboard and focus

Preserve ordinary keyboard navigation and canonical focus indicators. A text cursor, prompt cursor, selection, or active line must not resemble or obscure keyboard focus.

Terminal never authorizes key capture or shortcuts. Only confirmed canonical Product behavior may provide them, with an ordinary equivalent. Never override browser, operating-system, or assistive-technology commands, create traps, or require terminal knowledge.

### Live output and updates

Announce meaningful status changes through documented canonical behavior without reading every log line or decorative update. Distinguish current state from previous output and preserve recovery when a process fails.

Do not simulate live output, indefinite processing, or scrolling logs to make the website feel active. Continuous updates require a confirmed source, timing, and applicable accessibility behavior. Use controls, filtering, pause, or history only when confirmed requirements and canonical Product behavior support them; otherwise report the gap.

## Adaptation

### Responsive priorities

Preserve hierarchy, command integrity, input–output association, line order, actions, and system context as space changes. Reflow surrounding content, stack related regions, wrap safely, and use supported overflow only for content whose syntax requires it.

Do not preserve a desktop terminal viewport at the expense of readable text or task completion.

### Mode behavior

Terminal does not select mode. Resolve an explicit canonical `light` or `dark` mode before rendered work or canonical component selection. Use that mode's separate semantic mappings and component bindings; do not default, fuzzy-match, or derive one mode from the other.

Verify foreground, background, borders, selection, cursor-like marks, syntax distinctions, status, focus, and output hierarchy in the resolved mode. Do not simulate a dark terminal inside another mode or assume Terminal requires dark appearance.

### Content and localization resilience

Keep prose, labels, actions, help, errors, and annotations localizable. Preserve code, commands, identifiers, paths, and machine output exactly when they are not translatable, while explaining them in the user's language.

Support script coverage, bidirectional text, punctuation, text expansion, and locale-aware values without forcing the whole page into a left-to-right terminal model.

### Inclusive and cognitive resilience

Preserve semantic structure, keyboard access, visible focus, contrast, reflow, zoom, text spacing, target clarity, and non-color communication.

Keep prompt, command, output, link, selection, focus, status, and error distinguishable without relying on color or font alone. Avoid weak secondary text and excessive bright-on-dark contrast across sustained reading.

Use real text rather than terminal screenshots whenever practical. Provide alternatives for meaningful screenshots, diagrams, and system output.

### Performance and asset restraint

Prefer live text and supported structure over canvas rendering, video backgrounds, animated simulations, large raster terminal captures, and effect layers.

Do not add animation, noise, glow, or repeated system output as decorative payload.
