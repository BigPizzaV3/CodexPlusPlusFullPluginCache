# Quality programmes

Read [modes](../instructions/references/modes.md). For connected work read [connection](../instructions/references/connection.md), [change control](../instructions/references/change-control.md) and [human decisions](../instructions/references/human-decisions.md).

Agree objective, scope, baseline, outcomes, practical milestones and deliverables. Standalone: produce a useful plan with owners/dates when known and explicit gaps. Use [conflict resolution](../conflict-resolution/SKILL.md) for conflicting needs or implementation obstacles.

Connected: describe quality-programmes, programme-milestones and programme-deliverables; retrieve existing matches and supporting records. Create parents before children only after an exact preview. Link actual proof rather than treating a target date as completion.

A quick-win deliverable must identify the actual process/document it changes if required by the descriptor. A proposed process-map change inherits the mapping skill's final-only upload gate. Do not mark deliverables done or decide objective status. Do not claim reminders/background execution; scheduling requires a separate supported authorised capability.

Example: a 90-day plan may have useful milestone outputs without a fixed number of tasks. If a milestone depends on an unresolved policy decision, show the dependency and decision-maker rather than treating it as agreed.
