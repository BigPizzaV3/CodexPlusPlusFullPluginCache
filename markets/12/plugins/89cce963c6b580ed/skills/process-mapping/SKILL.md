# Process mapping workshop

Read [modes](../instructions/references/modes.md), [hierarchy and perspectives](references/hierarchy-and-perspectives.md) and [existing maps and impact](references/existing-maps-and-impact.md). Before any upload also read [connection](../instructions/references/connection.md), [change control](../instructions/references/change-control.md) and [human decisions](../instructions/references/human-decisions.md).

This workflow develops the map IN CHATGPT FIRST. Write no interim nodes, workshop notes, conflict hypotheses or provisional map changes to Doctilla. A branch review or generic "save progress" during the workshop means a user-held draft pack, not a database write. Explain this distinction if needed. Reading authorised existing context is allowed.

For a new map, open with: "Describe at a high level how your company operates: what you provide, who you provide it to, and how work moves from an enquiry or need to delivery and support. If you have an organisation chart, upload it now; otherwise we can work from your description."

Summarise the account. Propose a hierarchy of departments > macro-processes > procedures > work instructions. Explore roughly 5–9 macro-processes across the agreed company/scope and roughly 5–9 procedures per macro-process as guides only. Adapt for small/large organisations; no forced counts, duplication or blanket instruction generation. Work instructions are as many as genuinely needed, possibly none.

For an existing connected map, retrieve and summarise it as the baseline, then ask what changed or needs improvement. Do not repeat the whole discovery interview or build a parallel replacement by default. Failed/incomplete retrieval is not absence. Keep IDs in the working copy.

Work through one useful branch at a time, accepting a different order. Give outcome-oriented names and scope boundaries; explain alternatives. Develop purpose, triggers, inputs/outputs, activities, owner, handovers, records, controls and useful measures proportionately. Distinguish current state from future improvements; never conceal unresolved change in an as-is map.

At natural checkpoints ask whose perspective is missing, what the people doing/receiving the work would dispute, and what examples would resolve it. Record actual versus hypothetical views. Clarify facts, language and legitimate variants first; use [conflict resolution](../conflict-resolution/SKILL.md) for genuine incompatible needs/policies. Never simulate consensus.

Walk through normal work, an exception and cross-department handovers. Review the complete final hierarchy, process cards, flow/interfaces, responsibilities, decisions, actual reviewers and explicit exclusions. Unresolved material conflicts keep the affected branch provisional. An explicitly agreed subset may exclude it.

If connected, show the final upload difference plan and impacts before approval. If the user already explicitly approved this exact final package and displayed writes, do not ask twice. Refresh target state, reconcile conflicts, then save only that package through existing tools. No native map versioning, transactions, rollback or history migration is promised. Read back the affected hierarchy and issue a receipt.

If disconnected, export the same agreed package. For pause/resume use [the mapping pack](templates/mapping-pack.md). No automatic upload occurs after later connection.

Example: the user likes the procurement branch but is still debating production. Keep both in ChatGPT; branch agreement is not final upload approval. If a prior map is accepted unchanged, report no write needed.
