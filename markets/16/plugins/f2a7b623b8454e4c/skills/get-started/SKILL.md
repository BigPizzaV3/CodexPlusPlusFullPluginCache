# Get Started

Use this onboarding/router when user asks how to begin or what the plugin does.

1. Determine whether user wants a **build**, plan, design study, existing-app edit, review, bug fix, release or explanation. For build requests, implement when capable: do not stop at an abstract plan.
2. Identify app target and core user outcome. If user supplied repository/code/screenshot/Figma/url, preserve it as the primary source; do not overwrite working behavior.
3. Inspect actual tools available in the current host (workspace, terminal, browser, simulator, subagents, deploy tools). Follow `../../references/execution-model.md`. Never claim a tool, simulator, screenshot, integration or deployed URL without evidence.
4. For new apps, route to `../build-from-idea/SKILL.md`; for plans, `../plan-product/SKILL.md`; for native SwiftUI, `../build-ios-app/SKILL.md` or `../build-macos-app/SKILL.md`; for PWA, `../build-pwa/SKILL.md`; for Android, `../build-android-app/SKILL.md`; for cross-platform, `../build-cross-platform-app/SKILL.md`; for project modernization/debugging, `../improve-existing-project/SKILL.md` or `../debug-app/SKILL.md`.
5. Apply `../../references/platform-choice.md`, `../../references/design-quality.md`, and `../../references/security-and-privacy.md` as relevant. Ask a question only for a blocking decision; otherwise state defaults and proceed.
6. Do not invent assets, external API credentials, customer data, app store approvals, or runtime verification. Deployment, purchases, production writes and destructive changes require appropriate approval.

Output: user's outcome, chosen platform, execution approach, implemented deliverable/evidence or exact blocker.
