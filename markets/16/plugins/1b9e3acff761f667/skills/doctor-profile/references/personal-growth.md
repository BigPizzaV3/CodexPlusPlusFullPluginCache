# 完成稿と修正から、自分専用の作り方を育てる

動画台本、動画編集素材、サムネイルを本人の指示で修正し、修正版を渡した後の共通手順。音声・文字・画像への書き込み等、修正指示の入力方法を問わない。「この修正を独自スキル化して」「独自スキルを更新して」「これを見本にして」という直接依頼にも使う。本人設定や旧マニュアルがなくても開始する。旧GPTの5000文字・5つの質問・現行マニュアル提出は、このフローの前提にしない。

## 1. 完成した修正版を先に渡し、2つを独立して尋ねる

修正を実行して成果物を渡した後に、今回変えたことと今後へ引き継ぐ候補を2〜4点で短く示す。例えば「冒頭を患者さんへの問いかけにした」「専門語の初出に日常語の説明を添えた」「正方形の挿入画像では文字を減らした」。実際に行った変更だけを記す。解釈が推測なら、その点と適用条件を示す。

続けて、次の2問を必ず別々に出す。対象名は今回の完成稿・素材の名前に置き換える。

> 1. 今回の完成した［動画台本／動画編集素材／サムネイル］を、見本としてプロジェクトのソースに登録しますか？
> 2. 次回のために、今回の修正を反映した独自スキルを登録・更新しますか？ 今回のような修正を繰り返さずに済むよう、上の変更点を自分専用の作り方にまとめます。
>
> 「両方はい」「見本だけ」「独自スキルだけ」「今回は不要」で答えられます。

本来の制作を質問への回答待ちで止めない。未完成の案、音声の各発言、内部レビューの修正ごとには尋ねず、本人向けの修正版が一段落した時にまとめる。「本文だけ」等で追加案内を明示的に不要とされた場合はその指定を優先する。

制作メモに `本人／分野／成果物ID・版／質問済みの版／見本の回答／独自スキルの回答／実行状況` を記録する。同じ完成版へ重複して質問しない。新たな実質的修正があれば新版として扱い、前の選択を無断で新しい修正への同意にしない。「今後も両方登録して」「今後は聞かない」等の継続指定は、その人・分野・指定範囲で引き継ぐ。登録作業そのものや登録結果を伝えた後に、同じ2問を再発火させない。

## 2. 回答の扱い

| 回答・既存指示 | 実行 |
| --- | --- |
| 両方はい／1も2もはい | 見本と独自スキルの両方を作成・更新し、保存できる範囲を実行 |
| 見本だけ／1だけ | 見本のみ。独自スキルを作成・更新しない |
| 独自スキルだけ／2だけ | 独自スキルのみ。完成稿全文を新しい見本として登録しない |
| 今回は不要／両方いいえ | 登録・更新せず、現在の成果物を残して終える |
| 片方だけへの明確な回答 | 回答がある側は実行し、もう一方は未回答として短く確認する。未回答を同意にしない |
| 2問に対して単に「はい」等、対象を判別できない | 「見本と独自スキルの両方でよいですか？」の一問だけで対象を確認 |
| 初めから「完成したら両方登録」「この修正を独自スキルへ反映」と明示 | 指定した側は追加の承認を求めず実行。未指定側への提案だけを必要に応じて出す |

本人が提示済みの変更点を採用したら、旧差分モードの固定確認文を再度挟まない。一般的な「修正版OK」は完成稿への採用であり、保存への回答がまだなければ2問を出す。本当に不明な保存先・本人の取り違え・矛盾するルールの採否だけを確認し、無関係な再設定は求めない。

## 3. 独自スキルを、次回そのまま使えるMarkdownにする

[独自スキルひな形](../assets/personal-skill-template.md)を使い、差分メモだけでなく、判断条件と手順が揃った**全文の実ファイル**を作る。ここでいう独自スキルは、本人のProjectソースに置く再利用可能な作り方であり、共有プラグインのコード変更や実行環境へのネイティブSkillインストールではない。

| 分野 | 標準ファイル名 | 主な適用条件 |
| --- | --- | --- |
| 動画台本生成 | `独自スキル_動画台本生成_最新版.md` | 本人の動画台本の新規作成・改稿・3回喋るの台本化 |
| 動画素材作成 | `独自スキル_動画素材作成_最新版.md` | 本人の差し込み画像・動画・図解・編集納品一式 |
| サムネイル生成 | `独自スキル_サムネイル生成_最新版.md` | 本人のサムネイル案作成・画像修正 |

ファイルには本人またはProjectの識別、分野、版・更新日・前版、起動条件、必要入力、制作手順、具体的ルール、適用条件と例外、根拠となるBefore／After、今回の変更履歴、採用状態を必ず含める。初回は `v1`、更新は `v2` 以降等、同じ方式で版を進める。最新版の安定したファイル名と、本文内の版・更新履歴を両立させる。

更新前に、同じ本人・分野の既存独自スキル、台本マニュアル、素材設定を実際に読む。既存マニュアルがその分野の運用原本なら、内容を保持したままそれを更新するか、明示的に後継となる独自スキルへ統合し、旧原本の版と後継先を記す。同じ分野の相反する「最新版」を新旧2つ作らない。登録済みなのに読めない場合は読める範囲で改訂案を作り、統合未完了とする。旧内容を推測して上書きしない。

同じルールはIDを保って更新し、重複追加しない。最新の明示指定により古いルールを置換する場合は旧ルールの廃止と理由を履歴に残す。矛盾の解消が本人の意図だけでは判断できなければ、その箇所だけ保留する。本文に残すのは有効なルールであり、廃止済みルールを同じ優先度で併記しない。

### 学びにする範囲

- 今回の指示とBefore／Afterから確認できる変更を使う。原文のBeforeが取得できない場合は「未取得」と記し、本人の修正指示・完成版を根拠にする。差分を創作しない。
- 一回の修正は、まず同じ用途・条件に適用する。「この場面の文字を減らした」から「常にすべての文字をなくす」へ広げない。「今後は必ず」の明示や複数の採用例がある場合だけ、その根拠に合う継続ルールにする。
- 今回のテーマ・CTA・話題順・素材そのものと、次回も使う作り方を分ける。案件限定の変更は条件つきの例として保持する。
- 医学的な数値・効果・診断・因果・禁忌の修正は、作風として恒久採用しない。主張の根拠は案件ごとに再確認する。具体的な臨床経験は本人の事実として出典と使用範囲を保持し、他の医師へ移さない。
- 修正されていない箇所を新しい好みとして勝手に学習しない。採用が未確認の推測は有効ルールから分け、「未採用の候補」とする。

[更新判断](update-rules.md)も参照する。この2問への回答は本人のProject内への反映についての同意であり、Dr.SHI-GYO全員への共有や公開プラグイン更新への同意ではない。

## 4. 見本を保存する

[見本ひな形](../assets/project-example-template.md)を使い、採用した版・用途・見るべき点を付けた実ファイルを作る。台本では採用した**完成全文と文献**を含める。説明用の短い抜粋だけを完成見本と呼ばない。完成HTML等の原本があればそれも保持し、Markdownとの版を合わせる。プロンプター稿しかない場合は、その用途を明記する。

素材・サムネイルでは、選んだ実画像・実動画のファイル名、挿入位置・台詞、比率、表示方法、採用したデザイン、元の制作物の版を示す。Markdownにファイル名を書いただけで実素材まで保存されたとは扱わない。Projectが受け取れる実ファイルは一緒に登録し、動画等を登録できない場合は本人の確認済み保存先への参照と説明を用意して、未登録の実体を明記する。期限つきURLやこの端末だけのパスを、別環境でも常に読める原本として約束しない。

台本見本は1〜5本程度を目安にし、既存5本へ新しい見本を加える場合は「追加はできるが参照する見本を入れ替えるか」を必要に応じて案内する。本人の選択なしに過去の見本を削除しない。見本の登録だけでは独自スキルを自動更新しない。

## 5. 実際の保存と、できない場合の最小手順

1. 現在の本人専用Project・依頼された分野を特定する。読める既存情報は聞き直さない。共有プラグイン、他の医師のProject、公開サイトへ個人の見本・ルールを保存しない。
2. この環境に**当該Projectソースへ書き込める機能**が実際にあり、対象が明らかなら、選択済みの範囲を登録・更新してから読み戻す。一般的なファイル作成、別サービスへの保存、ローカルの `sources/` ミラー作成をProject登録の代わりにしない。同期された `sources/` が読み取り専用なら変更しない。
3. 読み戻して、本人・分野・版・変更点・完成本文・素材参照を確認する。古い同名ファイルが優先される状態を解消できない場合は、登録成功と断言せず残る操作を伝える。部分成功なら見本と独自スキルの状態を別々に報告する。
4. Projectへ直接書き込めなければ、選択した側のMarkdown実ファイルと必要な素材実ファイルを作ってダウンロードリンクを渡す。案内は「このファイルを、今回のProjectの『ソースを追加』から追加してください。既存の同名の独自スキルがあれば新版へ差し替えてください」のように最小限にする。画面の名称は確認できる実際のUIに合わせる。表示用コードブロックだけで終えない。
5. 直接登録できない場合の状態は「ファイル作成済み／Projectへの追加待ち」。本人が追加完了と言ったら、可能なら実際に最新版を読み戻し、読めなければ「追加の申告あり／読み戻し未確認」と区別する。保存した、覚えた、独自Skillをインストールしたとは言わない。

完了報告は「見本：名前・版・状態」「独自スキル：名前・版・今回の主なルール・状態」を短く示す。不要と回答した側を作って追加させない。ユーザーにJSON・APIキー・コマンド入力を要求せず、利用できない保存機能を増やすためだけに外部サービスの設定へ誘導しない。

## 6. 次回から使う

制作の開始時に、実際に参照可能なProjectソースから**同じ本人・同じ分野の採用済み最新版**を読む。指示は現在の本人の明示指定、採用済み独自スキルの適用条件、共有プラグインの標準手順を照合し、矛盾する場合は今回の明示指定を優先して必要な範囲を記録する。医学的な正確さや本人事実の確認は文体指定で省略しない。

独自スキルが未登録なら通常の制作を始める。登録済みなのに読めないときだけ、保存先または最新版の添付を短く案内する。毎回プロフィールを最初から聞いたり、「独自スキルを使って」と言わせたりしない。台本向けルールを画像や他の医師へ無条件で流用しない。登録によるモデル自体の学習・全チャットでの永久記憶を約束しない。
