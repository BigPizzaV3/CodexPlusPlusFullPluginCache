# Assist with registration

Read [the shared workflow rules](../../references/workflow-rules.md).

1. Resolve the event and attendee. Reuse profile details the user has supplied or authorized. Ask only for missing required non-password answers or ambiguous choices. Never ask for account passwords or other authentication credentials in chat or an embedded form. Never invent attendee details, dietary preferences, consent, or eligibility; use fictional data only for an explicitly requested test.
2. Call `swoogo_get_registration_form` for field definitions, choices, and validation. This tool also supports external website builders and may return password-field metadata. For chat registration, exclude any password field identified by its type, name, or label, including custom field IDs. Never place password values in `additional_fields`, other MCP arguments, generated defaults, or chat. Keep its submission token private. Resolve registration types and prices using `swoogo_registration-types_get` with `include_pricing: true` when needed. Do not assume every event or type is free.
3. Call `swoogo_get_registrants` with `event_id` and the exact email before creating. If a matching registration exists, report it or update it as requested. Clarify multiple matches; never create a second registration just to avoid resolving the first.
4. For a new registration, call `swoogo_create_registrant` with `event_id`, `email`, and supported common fields. Put `reg_type_id`, `job_title`, `phone`, and discovered custom fields in `additional_fields`; map choices to the actual IDs. Set `send_email` true only when the user requested a confirmation email, otherwise false. If the user wants to fill a form themselves and requests a confirmation email, use `swoogo_registration_form` instead of also creating the registration. The current embedded form submits with `send_email: true`; for registration without email, use the programmatic create workflow with `send_email: false`. The hidden submit tool belongs to the UI.
5. For an existing registration, read it and call `swoogo_registrants_save` with `registrant_id` and only requested changes. This update tool accepts `reg_type_id` and `job_title` at the top level. A cancellation must be explicitly requested; do not substitute it for deletion or a refund.
6. Resolve requested sessions with `swoogo_get_sessions`. Check event membership, times, availability, and the attendee's current selections. For a normal session addition, first call `swoogo_add_registrant_to_session` with `validate_only: true` and without `waitlist`. On successful validation, commit the requested addition with `validate_only: false`. Do not override capacity unless specifically authorized.
7. A waitlist is a different outcome from enrollment. Use `waitlist: true` only when requested or after the user chooses it. Never combine waitlist with a validation-only check: the server ignores other options when waitlist is true and writes immediately. For removals/moves, use the update tool's `remove_session_ids`/`add_session_ids` after resolving the requested IDs; inspect partial results and read back selections before retrying.

If there is a charge or payment requirement, explain it and use a verified Swoogo event/registration link for the user's next step; never collect payment-card details or claim payment succeeded. Report the actual registration ID/status and confirmed session or waitlist outcomes. If a create times out, search by event and email before retrying. A confirmation email request is not proof of delivery.

An optional password question must not prevent registration: omit it and submit the other supported answers. A password definition, even one marked required for the website, is not by itself proof that the API requires it. If the API rejects a registration because password setup is required, stop that attempt and direct the user to the verified external event registration website. Do not ask for the password, generate one, retry with a placeholder, or add a password input to the in-chat UI.

When explicitly building an external registration website, password definitions may describe browser-only inputs. Their values must go directly from the attendee's browser to the returned registration API endpoint (`/api/register`), never through chat or MCP tools. This external workflow does not permit password inputs inside ChatGPT.
