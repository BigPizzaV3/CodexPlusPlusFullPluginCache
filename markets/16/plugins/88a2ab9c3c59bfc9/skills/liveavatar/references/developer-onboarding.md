# From demo to a working official sample

Keep the transition short and consistent across ChatGPT and Codex. Use the selected sample's own setup, environment names and prerequisites.

1. **Continue in Codex for building.** In ChatGPT, choose or confirm the sample and give a compact continuation prompt for Codex: “Use LiveAvatar by HeyGen to set up <sample> in a directory I choose. Follow its packaged skill, guide private local API-key entry, then run and verify it.” Tell users to open Codex, enable the same plugin, choose their directory, and paste that non-secret prompt. Do not invent a deep link, claim an automatic chat transfer, or claim local files exist before Codex creates them. If they explicitly prefer instructions in ChatGPT, provide those. In Codex already, continue in place without redirecting or asking them to install a second plugin.
2. **Choose a sample, without starting over.** Reuse a sample, framework or goal already mentioned. Otherwise ask one question about what they want to build and recommend one sample. Offer the web avatar as the general first app, sales agent for lead qualification, GPT Live for a speech-to-speech tutor, the matching LiveKit ownership model for Python agents, and HyperFrames for local animated overlays. Do not list six setup procedures at once.
3. **Open the developer portal.** Give https://app.liveavatar.com/developers?utm_source=plugin&utm_medium=plugin&utm_campaign=liveavatar_launch&utm_content=developer_onboarding with the label “Sign up / get your API key”. Existing users sign in and reuse an appropriate existing key; new users create their account there. The official API-key guide is https://docs.liveavatar.com/docs/faq/api-key. If authentication returns the user to another dashboard page, have them navigate to Developers afterward. Do not promise automatic sign-up, key generation, OAuth connection, free API credits or a specific post-login redirect.
4. **Enter the key privately.** Tell them to create or copy their key in the developer portal, then put it directly into the selected sample's ignored backend environment file. Never ask them to send the key in chat. The variable name and filename differ: the web sample needs backend env wiring; sales and LiveKit use .env.local; GPT Live and HyperFrames load root .env. Confirm presence without displaying values. Use the selected skill for details.
5. **Do useful work while they sign up.** In a coding environment, set up the requested checkout and install dependencies in their chosen folder while credentials are pending. Do not call authenticated provisioning or start a billable session before required credentials and launch scope are clear. In ordinary web chat, provide the exact local steps and offer continuation in Codex, rather than saying code has run.
6. **Launch and verify one sample.** Explain any extra OpenAI, Anthropic, LiveKit or Claude requirements only for the chosen path. Report the actual ready signal, URL and checks performed. The human grants microphone access and confirms speech when the agent cannot observe it. Show one prompt/persona customization location, not a whole API tutorial.

V1 has no account connection. Signing into the LiveAvatar website does not give this plugin permission to read credits, create avatars, or fetch keys. Future OAuth can improve account-aware setup, but these workflows must work without it. Website sign-up and developer API setup are separate from the free anonymous demo sessions.

## Private local entry helper

The package includes `../scripts/configure_key.py`. This is a local terminal helper, not a built-in Codex credential dialog and not a ChatGPT iframe input. Read the helper before offering it. It uses Python 3.9+ standard-library hidden input and makes no network calls.

After selecting and preparing the project, give the user a runnable command with the actual absolute helper path and project directory:

`python3 <plugin-path>/skills/liveavatar/scripts/configure_key.py --project-dir <project-directory> --sample <web|sales|livekit|gpt-live|hyperframes>`

Have the user run it directly in their local terminal. Do not launch a tool-owned prompt and ask them to send its input through chat. The helper refuses noninteractive input, requires an ignored and untracked environment file, preserves unrelated settings, and saves with owner-only file permissions. It refuses overwriting a configured value unless the user explicitly chooses `--replace`. It accepts blank template entries. Never print or read the resulting environment file back into the conversation. For the web sample, complete the backend environment-variable wiring described in its skill.

The helper reports local save status only, not API validity. Verify through the running backend without returning credentials or upstream bodies that contain them. Hidden entry avoids chat and terminal echo, but it is not an encrypted vault or isolation from a local process that can read the project. Do not promise the key is inaccessible to Codex. Existing repository setup prompts can be used privately in the user's terminal where needed; they may have different masking behavior.
