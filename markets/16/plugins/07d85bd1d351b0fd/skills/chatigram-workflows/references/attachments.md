# Attachment access and consent

Use read_conversation and read_attachment with the authorized organizationId, conversationId and messageId. Native access returns incoming image/audio content up to 20 MiB without paid processing. A delivery receipt or metadata does not establish understanding; describe only visible content and request text when needed. Do not claim direct voice understanding.

Optional analyze_attachment/transcribe_attachment and corresponding nodes send the attachment and instructions to OpenAI through the selected connection and may incur charges. Before adding, binding or invoking them, obtain approval for that service, account, transferred content and spending scope. Never use paid processing as a silent fallback. Use attachment_processing_status for pending work; retain the same message, connection and processing settings on retries, and report unknown outcomes without starting another charge.

Measure the complete UTF-8 JSON-RPC envelope before writes, including Base64 expansion and JSON escaping. The MCP request cap is 256000 encoded bytes. Existing published calls retain their 240000 UTF-16-code-unit structured-result limit, including Unicode and legacy filtered/sorted read_records. Explicit read_records pageSize, columns, countOnly or includeCount opts into a 220000-byte row-result budget and a 240000-byte structured-result budget. The nine new tools (Pages, execution_outputs, workflow_dependencies, run_scheduled_once and add_schema_columns) also retain the 240000-byte budget. These differ from the 20 MiB native incoming attachment cap, the 256000-character Page definition cap and native Page HTTP envelope limits. Use smaller atomic batches, record projections or definitionPart reads when needed. An explicit oversized-field error is not silent truncation. Never fabricate Base64, file IDs, uploaded URLs or a larger server allowance from a successful compact-image workaround. Receiving a file, accessing its bytes, supporting its format and understanding its contents are separate outcomes.
