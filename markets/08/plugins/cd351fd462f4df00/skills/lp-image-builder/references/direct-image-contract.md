# Direct finished-image contract

New structures use schema 1.6 with workflow schema 1.5; older structures retain historical validation and approval views for reading. `source_ledger` and `authentic_proof` enforce the truthful order customer face → handwritten feedback → verified fallback. Customer faces and handwritten feedback require exact content/asset sources plus explicit scoped usage permission and privacy clearance. Permission/privacy ledger records must bind hash-verified external JSON evidence authored by a user or controller, never the model, and its asset/use/scope/expiry/constraints must match the proof item; never fabricate a customer, face, feedback, testimonial, or permission. `cta_strategy` keeps one primary action, while `direct_call` is an optional secondary action only when verified number and availability sources contain exact `phone_e164` and `availability_copy` values. Enabled calls use a baked exact label plus a transparent anchor overlay with exact `tel:`, availability/tracking markers, and 44×44px minimum mobile geometry. Every N-1 boundary fixes a semantic/copy/visual/layout `bridge_plan`; continuity and whole-page review copy it exactly, with arrows supportive only.

## Authority boundary

The workflow requires six distinct human/controller decisions:

1. approval of the single structure document;
2. selection of one FV candidate after reviewing a presentation containing every candidate's actual pixels;
3. approval of the selected 390px FV direction after an FV-only review;
4. approval of the page continuity plan after FV approval and before section 02+ generation;
5. approval of the finished ordered section images after complete whole-page review and tradeoff disclosure;
6. approval of the manifest-bound runtime source mapping and browser-QA evidence after the route is assembled.

Record each approval in one of two forms. Use an `external-approval-receipt` only when its bytes were genuinely supplied by the user/controller. Otherwise, after an explicit conversation decision, the model may create [conversation-approval-record.template.json](conversation-approval-record.template.json) with `decision_provided_by: user|controller`, `recorded_by: model`, exact decision evidence, exact scope, and the canonical subject digest. Never describe a model-recorded file as externally authored.

The structure approval binds the exact authoritative JSON path/hash, ordered structure-section digest, and (for 1.6) approval-contract digest. Use the shared `structure_approval_subject` helper. The [source and approval-scope contract](../../lp-structure/references/skill-contract.md#source-and-approval-scope) governs full/partial/hypothesis decisions. Only a full design decision advances image production; it never retroactively verifies original sources. An unset `href` can remain null through image creation, but interactive assembly requires a safe supplied URL with exact field-value source binding. A deterministic Markdown approval view is generated from that JSON, binds its source path/hash, and is validated byte-for-byte; it never becomes a second authority. New production transitions require structure 1.6; legacy JSON cannot be relabeled to bypass the scoped contract. Existing approved source records and image bytes retain their provenance during handoff. The FV approval uses scope `lp-fv-direction` and binds the creative comparison, selected source FV, exact shown 390px presentation, review artifact, and outcome-based quality gate. The continuity approval uses scope `lp-page-continuity` and binds the approved structure plus the complete page continuity plan. The assembly approval binds the complete canonical assembly payload, including continuity plan, whole-page review/composite, images, dimensions, loading, accessibility text, and overlays. A generic `OK` applies only to the immediately preceding shown artifact and declared scope; it cannot approve unseen artifacts or a later phase.

## Phased design boundary

Use workflow schema 1.5 in [workflow-state.template.json](workflow-state.template.json) and run `scripts/validate_workflow_state.py` at every transition. The only sequence is `structure-approved` → `fv-selection-pending` → `fv-review` → `fv-direction-approved` → `page-continuity-approved` → `sections-complete` → `whole-page-reviewed` → `assembly-approved` → `assembled`.

If the user/controller explicitly rejects both first-batch directions and requests the one permitted revision, retain the original pending state/comparison and write a distinct revision-outcome comparison with `selection_status: revision-requested`, null selection fields, and the concrete rejection observations. Bind the exact request in a separate `lp-fv-candidate-revision` receipt. The replacement batch returns to the neutral `selection_status: pending` boundary, freezes its own distinct pending state/comparison, and must end its presentation turn before an exact later-turn selection.

The workflow state file stays outside one dedicated `artifact_root`. That root is closed-world: its recursive regular-file inventory must equal the ledger path/hash entries exactly. Do not place unlisted images, crops, screenshots, review-like images, or code there. Do not keep workflow artifacts elsewhere and bind them back into the state.

- Before `page-continuity-approved`, section 02 and later do not exist, including fixtures and placeholders.
- Before `assembly-approved`, outputs are limited to image assets, review artifacts, manifests, and externally supplied receipts. Do not create HTML, CSS, JavaScript, TypeScript, TSX, React, runtime assets, or browser-rendered design screenshots.
- Never switch to hybrid, code-native, decomposition, or browser-screenshot fallback. Stop when a finished image cannot be produced.
- Every new-schema section is an independently host/session-generated or newly user-provided finished PNG, bound to a concrete source-evidence file and the exact source hash. Full-section raster composition, relabeling an existing raster, and local patching are legacy/archive-only and cannot authorize new output. If a correction is needed, regenerate the full finished image or obtain a new finished user image.
- The whole-page PNG is review-only. Build it by exact vertical composition of the section PNGs. Never use it as the design source for the FV or any section.

## FV quality gate

For schema 1.5, treat `fv_handoff` as an outcome contract and `fv_content_budget` as its pre-generation information budget. Assess traffic/source-message match, awareness, category familiarity, offer complexity, decision risk, proof strength, visual explanatory power, action readiness, and regulatory class. The source offer and action must exactly bind the five-second offer and CTA. The scan contract fixes identifiable outcomes for relevance, what-it-is, core benefit, trust basis, and next action, while allowing copy, visual, proof, or CTA evidence as appropriate; a visual that explains category or trust does not require duplicate copy. Select `lean` (90 non-whitespace characters, 5 items, 1 proof), `standard` (140, 7, 2), or `reassurance-heavy` (180, 8, 3) as a context-selected planning guardrail, not a universal hard pass/fail threshold. Record exact counts and `within-profile|context-exception`; an exception requires concrete context and remains subject to the hard intrinsic-render gate. Every non-empty first-section copy leaf must be exactly and completely covered in order by stable visible items. Require one dominant and one primary action; allow at most one visible support, audience, and provider item; keep every micro item at 24 non-whitespace characters or fewer. Bind visible proof phrases to verified claims. A must-show fact may use a short exact claim-supported phrase instead of its full explanatory sentence. Bind provider, identity, credibility, and belief decisions to visible/deferred items. Every deferred item names a real later section, explains the deferral, and appears in one of that destination's nested copy leaves; deferred proof also binds a verified claim authorized for that destination. Belief shift supplies an exact visible expression in first-section authority copy. Visible credibility binds exact expressions to both authority copy and verified source-ledger claims. Provider recognition is independent of audience identity; visible requires the exact provider name in authority copy and deferred requires null. `visual_job` states what the visual must communicate, never a subject/layout/position/photo/badge/style/image-method recipe.

Before FV outcome review, produce exactly two materially different finished 390px candidates in one batch, each 600–900px high, with distinct paths/hashes and at least 3% differing canonical decoded RGBA pixels. Normalize generated/attached PNGs with `scripts/normalize_candidate_png.py` before recording candidate hashes, evidence, ledger, or presentation; only the normalized public 8-bit non-interlaced RGB/RGBA bytes may become candidates. Canonical comparison zeroes RGB at alpha 0 and premultiplies partially transparent RGB, so invisible RGB payload changes do not count. Conservative color, luminance, and edge-variation checks use the same canonical pixels to reject tiny, flat, and trivially perturbed raster inputs; these checks do not prove design quality. Source creation must come from an actual host/session image-generation invocation in that turn or an actual user attachment. Each normalized candidate binds its exact hash plus concrete host invocation/result asset identifiers or user message/attachment identifiers. Distinct candidates require distinct host result-asset IDs or distinct `(message_id, attachment_id)` pairs; one source reference cannot be relabeled across hashes. A bare provenance enum, handwritten generation claim, or raster relabel cannot pass.

Record the approved budget content and digest in the creative comparison. For each candidate, record the exact visible item IDs in order, observed character/item/proof counts, an explicit empty unplanned-text inventory, source-message/offer/action match, all five scan outcomes and their actual evidence modes, one primary action, and intrinsic 390px line fit (H1 at most 3 lines, support at most 4, CTA exactly 1; no nonuniform squeeze, condensed-to-fit, clip, or overflow). These rendered outcomes are hard gates even for a declared budget exception. Preserve an ordered, closed-world `fv_batch_history`: batch 1 is required; batch 2 exists only after a distinct user/controller revision request bound by exact message ID/text; batch 3 is forbidden. If the user rejects both initial candidates, batch 1 records `revision-requested` and no candidate-selection context or receipt. A selected batch records `selected` and retains the existing exact-ID selection receipt. Prior comparisons, candidates, hashes, and ledger entries remain immutable and cannot be overwritten or reused. If both candidates fail for the same density or structure reason, stop and return to `lp-structure` for a revised and reapproved budget.

Complete schema 1.2 [fv-creative-comparison.template.json](fv-creative-comparison.template.json) after actual session visual inspection. Candidate IDs use the exact safe form `candidate-<two-or-more-digits>`. Bind every candidate and reviewer input hash, all candidate-pair material-difference observations, provider/belief/proof/action evidence and locations, message-image alignment, hierarchy order/locations, readability, and concrete generic-substitution observations. In `fv-selection-pending`, both candidates remain neutrally unselected, rejection reasons and all selected ID/context/approval fields remain null, no section images or downstream artifacts exist, and the closed-world ledger is complete. Visibly present exactly both bound candidates and IDs, then end the turn. Only a later user/controller turn containing exactly one candidate-ID token, equal to the selected candidate, may establish selection and `fv-review`. A generic `OK`, same-turn decision, reverse choice, or ambiguous `candidate-01 or candidate-02` fails. Bind distinct presentation/selection message identifiers and the exact decision text into the selection subject. The portable runtime has no signed host/controller attestation API: validators bind the declared identifiers, evidence, hashes, and turn separation, but cannot authenticate who authored an identifier or prove aesthetic pixel truth.

At `fv-selection-pending`, calculate `pending_comparison_sha256` from the canonical selection-neutral projection and copy it into the comparison, workflow state, and current `fv_batch_history` entry. The projection includes ordered candidate image/provenance bindings, every inspection field except `selected` and `rejection_reason`, material-difference axes, presentation, reviewer inputs, and structure/budget/batch/validator scope; it excludes selection status, selected ID, selection context, selection approval, and the digest field itself. Before presenting, write that pending comparison under a batch-specific path and write a distinct workflow 1.5 pending-state file outside `artifact_root`; never overwrite either file. Immediately after the pending state validates, the host/skill records its path and actual file SHA-256 without asking the user to manage them. A later selected/revision state uses a different state/comparison file, records their exact bindings in `fv_transition` and batch history, and must be validated with both caller/host-supplied `--prior-pending-state` and `--prior-pending-state-sha256`. The validator checks actual prior bytes against the independent caller SHA before consulting the mutable current-state binding, then revalidates the frozen state's complete ledger-bound bytes while allowing only unbound later-created files and compares the current neutral projection to the snapshot. Rewriting the prior file and recomputing current/prior hashes, receipts, ledgers, or digest fields therefore cannot redefine what was presented. Selection and revision approval subjects both bind the prior pending-state SHA/path, pending-comparison binding, and neutral digest. Observation, material-axis, presentation, provenance, or candidate-order changes require the one permitted new presented batch; they cannot be introduced at selection time.

Complete [fv-outcome-review.template.json](fv-outcome-review.template.json). Bind the creative comparison, selected observations, exact budget content/digest, and selected observed budget inventory; source, shown, and selected bytes must agree. The selected source image itself contains the complete visible CTA label and baked control. Runtime may add only a transparent interactive hit area over it, never a blank plate, runtime-only label, or visible duplicate. Schemas 1.1/1.2/1.3 retain their legacy read-only behavior.

## Page continuity gate

After FV approval, create [page-continuity-plan.template.json](page-continuity-plan.template.json) before generating any later section. Lock one shared visual system, the page's band rhythm, all approved N-1 adjacent boundaries, and every repeated-series cue invariant. Boundaries may use `visual`, `layout`, `open-loop`, `contrast`, `copy`, or `mixed`. Copyless paths are first-class; `transition_copy: null` is valid and expected for non-copy mechanisms. Only `mechanism: copy` requires transition copy. A decorative arrow may support a transition but cannot be its only mechanism.

The structure must explicitly include `series_assessment` with `present|none`, rationale, and a candidate inventory that assesses every section. For `present`, the `(section_id, component_id)` keys marked `series_candidate: true` must exactly equal the union of every `repeated_series.members` key; an unassigned candidate fails. `none` requires an empty series list and no candidates. A conservative detector rejects `none` when multiple numbered `STEP n` labels are visible, but human/controller review remains responsible for unnamed patterns such as cards, pricing plans, or comparison rows.

Repeated series may span contiguous sections or components. Every planned member must retain all recognizable cues. Missing members, changed cues, or identity drift fail the gate.

## Whole-page review gate

Build the review PNG by exact vertical composition, then complete [whole-page-review.template.json](whole-page-review.template.json). Review all N-1 semantic and visual seams, every section's Japanese text fit, and every repeated-series member. The approval-bound whole-page review also repeats the selected FV's hard render outcome: exact first-section image hash, 390px viewport, H1/support/CTA line counts, one primary CTA, no squeeze/clip/overflow, source-message/offer/action match, and every approved scan outcome with its actual evidence mode. The standalone final-manifest validator requires this record, so calling assembly validation without a workflow comparison cannot bypass the FV hard gate. Each boundary review must copy the exact approved `execution_cue`; each series and member review must copy every exact approved cue-invariant rule. A valid copyless boundary keeps `transition_copy: null`; do not add repetitive bridge copy merely to satisfy the review.

At intrinsic 390px, prohibit nonuniform glyph scaling, condensed-to-fit treatment, clipping, and overflow. The FV hard gate requires H1 at most 3 lines, support copy at most 4 lines, and the primary CTA on exactly 1 line. Require measured body text of at least 16px, supporting text of at least 14px when present, and line-height of at least 1.4. If FV copy does not fit within 900px, return to structure and reapprove a smaller or differently deferred budget; do not grow the FV. For later sections, increase section height, reduce or move decoration, or split the section and reapprove the changed structure; never squeeze text.

The validators prove declared artifact binding and review completeness. They do not inspect or establish pixel-level visual truth. Human/controller review of the intrinsic-size page remains required.

## Canonical assets

- One PNG per approved section, in exact approved order.
- Every PNG has intrinsic width exactly 390 pixels and a positive height; the first/FV PNG is additionally bounded to 600–900px in both workflow and standalone final-manifest validation. The portable public subset is 8-bit, non-interlaced RGB or RGBA with no PLTE/tRNS; convert other valid PNG encodings before approval.
- The manifest SHA-256 must equal the bytes assembled into the web project.
- The first section uses `loading: eager`; all later sections use `loading: lazy`.
- Every section supplies a concise `alt` and a longer `accessible_summary`.
- Image paths are canonical relative paths inside the caller-supplied project root.

The validator checks PNG signature, chunk framing, CRCs, IHDR dimensions, IDAT presence, zlib decoding, terminal IEND, paths, file hashes, order, loading, overlays, and the approval digest. It is read-only.

## Interactive overlays

Only `cta`, `form`, `map`, `accordion`, `video`, and `link` are allowed. Each overlay binds an image-coordinate region `{x,y,width,height}` inside the 390px image and has an accessible label. New-schema CTA declares `image_region_policy: transparent_hit_area_over_baked_control`; its label exactly equals the baked approved CTA label. Other overlays declare `interactive_only`. Static provider identity, proof, hierarchy, copy, and decoration are never supplied only by overlays. Older blank-region declarations are archive-only and cannot authorize new assembly.

At runtime, scale overlay coordinates by the rendered image width divided by 390. Do not crop the source image. A CTA overlay keeps hit geometry and an accessible label but renders no text or visible descendants. Before focus, the element and its `::before`/`::after` pseudo-elements must add no background, border or border-image, box-shadow, nontransparent outline, filter, mask, or other visible paint over the baked control. This pre-focus measurement does not prohibit a keyboard-only `:focus-visible` outline. Other overlays add only the interaction required by their kind; they do not supply static authority content.

## Approval receipts

Use [external-approval-receipt.template.json](external-approval-receipt.template.json) for genuinely supplied receipt bytes or [conversation-approval-record.template.json](conversation-approval-record.template.json) for a model-recorded explicit decision. `subject_sha256` is SHA-256 of canonical JSON using UTF-8, sorted object keys, and separators `,` and `:` with no extra whitespace.

For `lp-structure`, the receipt subject contains the structure `path`, file `sha256`, and SHA-256 of its complete ordered `sections` array. The structure file hash also binds the N-1 boundary and repeated-series plans. For `lp-fv-candidate-selection`, the subject binds the structure hash, caller-anchored prior pending-state binding, immutable pending-comparison binding/digest, candidate presentation path/hash/dimensions, all candidate hashes, selected ID/hash, distinct presentation/selection message identifiers, and exact later-turn decision text. `lp-fv-candidate-revision` binds the same frozen state/comparison/digest plus exact request message ID/text. For `lp-fv-direction`, the receipt subject contains scope `fv-only`, the structure binding, the independently finished FV binding and provenance, creative-comparison binding, last shown review artifact, and the complete FV quality result. For `lp-page-continuity`, the subject contains scope `page-continuity`, the structure binding, and page continuity plan binding. For `lp-direct-image-assembly`, the receipt subject is the final manifest validator's complete canonical payload: structure binding and receipt, continuity plan/approval/review/composite bindings, every section field and overlay, and the assembly policy. For `lp-runtime-assembly`, the subject contains the manifest binding, normalized `base_origin`, route, exact runtime source bindings, runtime map binding, and browser-QA binding.

Any continuity plan, whole-page review/composite, image, dimension, loading policy, accessibility text, overlay, order, path, hash, or assembly-policy change invalidates assembly approval and requires another whole-page review and approval artifact.

## Browser acceptance

At 320, 390, and 430 pixels verify:

- image order equals the manifest;
- adjacent image rectangles touch without a visible gap or overlap;
- no horizontal overflow or crop occurs;
- FV is eager and later sections are lazy;
- delivered asset hashes equal the manifest;
- overlays remain inside their reserved regions and work by keyboard;
- alt and accessible summaries are associated correctly.

Every rendered section image must carry explicit `data-lp-section-id` and `data-lp-section-order` attributes matching the manifest. Every overlay must carry `data-lp-overlay-section-id`, a one-based `data-lp-overlay-index`, and `data-lp-overlay-kind`. These are runtime acceptance markers, not decorative metadata.

After live checks, bind the exact runtime source path/hash list and section mapping with [runtime-assembly-map.template.json](runtime-assembly-map.template.json). Each manifest section image path must appear in the bound UTF-8 runtime source named by its mapping. This static declaration is auditable but is not sufficient evidence that the route renders it; comment-only or unused strings do not pass the live gate.

Bind the route, manifest hash, 320/390/430 DOM image order, served image hashes, no-gap/no-overflow results, overlays, and accessibility with [runtime-browser-qa.template.json](runtime-browser-qa.template.json). Obtain scope `lp-runtime-assembly` approval over the exact manifest, route, source, mapping, and QA bindings before entering `assembled`. Then validate the served route:

```bash
python3 scripts/validate_workflow_state.py /path/to/workflow-state.json --project-root /path/to/project --prior-pending-state /path/to/project/workflow-fv-batch-01-pending.json --prior-pending-state-sha256 <host-recorded-64-hex-sha256> --runtime-base-url http://127.0.0.1:3000
```

The runtime map and browser-QA schemas are `1.2` and both bind the same `base_origin`. In the portable public contract this must be exactly normalized `http://127.0.0.1:<explicit-valid-port>` or `http://localhost:<explicit-valid-port>`, with no credentials, path, query, or fragment. The CLI `--runtime-base-url` must equal that approved value. Remote origins are not silently permitted: stop and seek a future explicit contract and reapproval. Routes must begin with one slash; protocol-relative `//` values, backslashes, fragments, redirects, and any resolved origin drift fail.

The validator runs the bundled read-only Playwright probe from the caller project and fails closed if Playwright, its browser, the route, or any required marker is unavailable. It checks visible positive section geometry, intrinsic width 390, centering/aspect ratio, exact marker order, seams and horizontal overflow, alt/summary association, and overlay count/labels/bounds. The hash comes from the actual unique Playwright `Response.body()` observed for each page image request; a second `context.request.get` is forbidden because it can observe different bytes. Missing or ambiguous matching image responses fail.

Paint visibility rejects clipped/offscreen sections, effective opacity near zero, `content-visibility: hidden`, non-none CSS filter/mask/WebKit mask, and fully transparent image paint. After scrolling each section into view, the probe samples multiple points with `elementsFromPoint`; the section image or a manifest-bound overlay for that section must be topmost at a meaningful majority. Full or near-full sibling/fixed covers and unbound overlays fail. The observed JSON must exactly equal the bound QA JSON. The direct Python API similarly requires an injected live probe at `assembled`, so tests cannot silently substitute declared evidence.

This point-in-time observation does not prove future route state, visual meaning, keyboard behavior, link destinations, pixel-level truth, or cryptographic identity. Run and inspect the actual route before release even when the validator passes.

### Missing proof and unknown traffic

When every authentic-proof option is unavailable, use `selected_mode: none`, `items: []`, deferred credibility with empty evidence refs/expressions, and zero visible/deferred proof items. The trust-basis scan uses only `copy`: bind its exact answer into visible FV copy and its content-budget item, explicitly explaining that evidence was not supplied and what must be confirmed; never substitute a fictional testimonial, visual, badge, or verified claim. This is a usable hypothetical structure, not a claim of demonstrated effectiveness. When the actual traffic message is unknown, schema 1.6 may use `source_message_match: unconfirmed` only with `approval_contract.request.hypothesis_design: true`. Label traffic assumptions and planned offer/action as proposals; do not describe them as a verified source match. The proposed offer and action must still exactly match the planned FV. A known mismatch remains invalid.
