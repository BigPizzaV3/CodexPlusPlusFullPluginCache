# Test semantics and causal claims

Name a test from the layer that is isolated, not from the file that contains the variants.

| Test type | Fixed | Varies | Allowed conclusion |
|---|---|---|---|
| `territory_baseline` | selected Territory and all execution decisions | nothing; one build artifact | the selected Territory was rendered into a reviewable baseline; no comparative claim |
| `hook_package_discovery` | Body, CTA, destination, placement | angle, incident, execution | this complete package performed better |
| `angle_discovery` | execution, wrapper, Body, CTA | angle | this angle performed better under the fixed execution |
| `hook_execution_test` | angle, wrapper, Body, CTA | execution | this execution performed better for the fixed angle |
| `trend_wrapper_test` | angle, base execution, Body, CTA | wrapper | this wrapper performed better for the fixed creative |

Do not turn a Taste-approved Territory directly into an eight-package portfolio. Build and approve one `territory_baseline` first, then enter OPTIMIZE. Do not report an eight-package discovery portfolio as a pure Hook execution test when client pressure, funnel contradiction, measurement incident, deadline, and execution grammar all change together.

Every package records stable signatures for angle, execution, and wrapper. The validator checks equality only for layers declared fixed. A package-level discovery still needs those signatures so the winning territory can be decomposed in the next test.

## Opening-surface redundancy

For an initial `hook_package_discovery`, package diversity must be visible before the Body begins. A copy change inside the same chat shell, with the same message arrival and cut pattern, is usually an `angle_discovery`, not broad package discovery. If the learning question is which work incident earns attention, keep those incidents visually distinct: for example, client chat, calendar deadline, revision history, report anomaly, and meeting-document pressure.

Do not use a custom test name such as `common_body_reuse_forward_test` as a substitute for causal semantics. Common-Body reuse may be recorded as a separate engineering objective while the future comparison still declares one of the standard test types. A two- or three-Animatic review stays `EXPLORATION_ONLY`, carries no performance conclusion, and should not create the illusion of a controlled campaign test.

The same UI is useful when the question intentionally fixes execution. It is wasteful when the purpose is to explore distinct Hook Packages and the viewer would perceive the variants as the same ad.

## Audience preconditions

Some incidents require information the target may not see. Record `requiredDataVisibility` such as `crm`, `sales_outcome`, or `measurement_change_log`.

- `broad`: no special downstream visibility is necessary.
- `conditional`: the data visibility and interpretation risk are explicit.

If a conditional Hook loses, do not conclude that the angle is weak until audience access to the assumed data has been considered.

## Shortlists

Two or three Animatics may be made after human approval to compare comprehension or production risk. Mark them `EXPLORATION_ONLY` and `gating: false`. Their result does not authorize publication and does not replace the controlled batch.
