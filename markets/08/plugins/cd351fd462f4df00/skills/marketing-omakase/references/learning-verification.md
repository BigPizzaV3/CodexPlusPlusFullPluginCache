# 学びと検証結果の記録

案件への保存が依頼・同意された範囲で適用する。未接続の無料制作に保存や接続を要求しない。全会話の自動取得や、すべての外部AIが必ず報告する仕組みとは説明しない。

1. 成果物の版・観測期間・実績は既存の成果物/観測保存経路へ先に保存する。同じ実績を別の正本として作らない。
2. 再利用できる学びがあれば既存の `recordLearning` の現行schemaを読み、適切なkindで保存する。既存の学びに追記する場合はIDを再利用する。返却されたknowledgeAssetIdを保持し、保存応答を確認してから保存済みと伝える。
3. 現行tools/listに `reportKnowledgeVerification` があれば `operation=prepare` とknowledgeAssetIdで最新の学び・版・履歴を取得する。既存のlearning_loop権限と案件の書込権限が必要。ツールがなければ利用できないと伝え、同意済み案件のナレッジ詳細から「検証結果を記録」へ案内する。権限を迂回しない。
4. `operation=record` に同じknowledgeAssetId、取得したexpectedRevision、一つの報告に固定したoperationIdを渡す。観測した事実、判断の理由、出典のどの箇所で確認したか、限界・未確認事項、次に確認することを報告する。checkTypeは出典確認/source_check、制作・実行確認/execution_check、効果確認/outcome_checkを区別し、効果確認には対象期間が必要。出典だけ読んでも施策の効果が確認できたことにはならない。
5. assessmentはsupports/refutes/inconclusive。根拠なし・未計測・条件不一致ならinconclusiveとして不足と次の検証を残す。支持・反証を報告する場合は根拠を必ず付ける。外部AIの報告は自己申告の出典でありサーバー照合済みと呼ばない。制作完了や受領確認から成功を推測しない。別のAIが同意しただけでは実証にならない。
6. 通信失敗の再送は同じoperationId・同じ入力を使う。409ならprepareし直し、変更点を確認して新しい版に対する新規報告にする。失敗時は「未保存」と伝え、保存できたことにしない。
7. 保存後は返却された結果を表示する。proposalCreatedならオーナー・管理者の確認待ち。人による承認を代行せず、検証済み・成功・正式戦略へ自動昇格させない。既存提案や確認済みの学びへの追加報告は履歴に残るため、必要なら担当者へ再確認を案内する。

サーバー実績との照合が必要なら、利用可能な既存 `evaluateExperiment` の適用条件・予算・権限を守る。報告保存を理由に追加AI生成や公開、配信、計測設定変更、未承認の費用を発生させない。案件固有の文脈をチーム・グローバル共有に流さない。
