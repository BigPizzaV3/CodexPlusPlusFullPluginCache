# MyMarketerから資料の根拠を集める

接続先が公開するtool schemaを使う。案件ID、接続環境、認証情報を配布物に固定しない。

## 対象と入力を確定する

ユーザーが指定した案件をMyMarketerの `listProjects` で照合する。同名のCodex作業プロジェクト一覧とは区別する。複数候補から勝手に選ばず、本番とテスト環境も無断で切り替えない。

外部作成の草案を資料化する場合は `/mcp/quality` の `getStrategyDraft` と `getStrategyAuthoringGuide` を使用する。保存済みの戦略・根拠・仮説・判断、原資料の参照位置、返されたrevisionとstrategyContentHashを入力として固定する。草案を承認済み正本と表示しない。

既存の正式戦略は、公開されている `prepareMarketingJobPreview` と `getProductionGuidanceInputs` のschemaと返却内容を確認する。制作種別を捏造せず、取得できた戦略・承認済み判断の範囲を確認する。必要な本文が欠ける場合は、完全な戦略エクスポートをユーザー提供資料として扱う。LP・動画向けの部分的な文脈を完全な戦略と呼ばない。

資料制作だけの依頼で新しい草案を作成したり、正式戦略を書き換えたりしない。権限照会の失敗、欠落した判断、古いエクスポートを使った場合は、その状態を出典対応表に残す。

## 判断と根拠を読む

承認済みの判断と戦略本文を照合する。新しく具体的な判断がある場合は、その対象・承認範囲・日時を確認して資料へ反映し、戦略本文も既に書き換わったとは解釈しない。自動生成の判断をユーザーが個別承認したように表示しない。

判断の一覧や本文が省略されている場合は、接続先が提供する正式な読み取り手段で不足を補う。補えなければ不足を明示し、影響を受けない資料の下書きを続ける。競合する判断を日時だけで機械的に合成しない。

作業用対応表には、スライド番号／主張／案件と戦略版／原資料の参照位置・判断ID／取得日時と対象期間／区分（実績・目標・仮説・試算・提案）／不足を残す。

読者向けの出典行は、資料名・日付・ページ等にする。数値、顧客発言、競合評価を創作しない。実測がない内容を実績と呼ばず、予算が未承認なら提案とする。

接続なしの制作は「ユーザー提供資料、取得時点未確認」など、実際の状態を明示する。架空見本を使った試作は架空・例示と分かる表記を付け、実案件の初期値に転用しない。
