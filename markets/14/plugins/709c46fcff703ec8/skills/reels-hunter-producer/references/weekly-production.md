# Personal weekly production

Use this workflow for a weekly plan, a batch of ideas/scripts, or resuming an
existing production week. Finish the requested free planning and bookkeeping in
one turn when the necessary context is available. A saved week is planning, not
an automation or a publishing schedule.

## Resolve the brief once

Read current capabilities and selected project, relevant memory/goals/content/
outcomes, and available personal/brand DNA. Reuse explicit choices. Do not treat a
tracked author, a saved report or the project's generic name as the user's brand.
If the promoted subject is still ambiguous, ask one compact choice while doing
independent work. Persist the answer as a user-stated profile fact. Keep audience,
filming resources and creative defaults as labeled assumptions until confirmed.
Do not repeatedly ask for an already saved niche, goal or preference.

Use the user's chosen period and timezone; otherwise propose the next seven days
using the host's current date/timezone and label dates as suggested filming/content
slots. Do not create a recurring task just because a week or goal was saved.
Default to seven original scripts for a week when count is unspecified; reduce
only for a real constraint and explain it. Adapt to a requested different count.

## Select evidence efficiently

Start with relevant library favorites and saved analyses, then inspect a bounded
sample of recent feed candidates (normally 12–24, at most 36 unless requested).
Follow returned next.page/item_offset within a sampled upstream page; state the
sample coverage and never claim to have reviewed the full feed. Prefer a narrower
search to downloading the archive. Read only needed report sections: overview,
section__index, and returned semantic aliases when that tool schema permits them.
Follow next_offset/snapshot exactly; offsets count Unicode codepoints, not bytes
or JavaScript UTF-16 units. Honor min_interval_seconds and Retry-After on 429;
retry the same read after the interval without starting new analysis or paid work.

Filter by subject/audience/goal, practical filming effort, previous choices and
available dated evidence. Separate published_at and observed_at. Metrics are
saved snapshots, not owner growth or proof that a format caused performance.
Do not rank solely by absolute views; consider comparable-author baselines only
when eligible and sufficiently supported. Do not fill missing metrics with zero.
Do not infer footage, speech or an edit from a caption or a thumbnail. State the
source basis (caption, transcript, saved analysis, actual inspected frames).

Check relevant stored content for near-duplicate promises/examples, not just
matching titles. Choose varied audience problems and stages of awareness; do not
copy another creator's distinctive wording or structure scene-for-scene. For
each idea retain an actual source link/ID and a short reason it fits. A useful
original idea without external evidence may be included as an explicit hypothesis.
When promoting a product, check that each promised feature is available for the
intended audience. Label pilot features; a founder's working prototype is not a
publicly available feature. Do not promise views, revenue or a render duration.

## Produce a shootable packet

For every chosen item provide: proposed date, title, audience problem, reason for
selection, original spoken hook and complete voiceover, 3–5 practical shot/screen
directions, one clear CTA, target duration and effort, and source basis/link.
Write the actual spoken text, not an outline requiring the user to finish it.
Use tested product behavior and user's explicit facts; keep creative outcomes
as hypotheses. Readable effects and demo footage are instructions for filming,
not claims that an edit or recording has already been made.

Prepare one short batch-filming checklist (location, screen captures, props,
recording order and a reasonable time estimate labeled as an estimate). Group
similar setups together. Preserve the same factual promise across Instagram,
YouTube Shorts and TikTok; adjust on-screen opening/title/CTA when useful.
Do not invent connected destinations, footage or posted URLs.

## Save a resumable production week

Use one stable goal key, for example weekly-<brand>-<period-start>, and stable
numbered content keys below it. Read exact keys before creating/updating if they
may exist. An identical request should resume the existing week, not generate a
second competing plan. A requested alternative uses a clearly distinct key;
never silently replace user changes or delete earlier plans.

Save the goal with its measurable preparation criterion and concrete next action.
Use only live goal fields: the current contract has title, status,
success_criterion, next_action, timezone, optional due_at, and blockers; no notes
field. Put the shared weekly table/checklist in a supporting content record and
reference its exact key in next_action.
Save complete scripts using save_content_record(stage=script), goal_key and actual
reference kind/value pairs. The current reference kinds are source, analysis,
script, media, studio_project and publication; do not invent url or library_item
kinds. Keep producer-record links in notes unless a live typed relation supports
them. Keep each encoded record within the live contract's
limit (currently 6 KB including JSON/UTF-8 overhead), leaving margin for references.
Also respect individual field limits: current producer notes allow 1,000 Unicode
characters. The envelope allowance does not override that field limit.
Put a concise self-contained packet in notes, not a local file path or inaccessible
chat reference. If it cannot fit, split into a main content record and linked
clearly named continuation content records; keep the complete spoken script in
the main record when it fits and shots/evidence in a linked -shoot record. Include
both directions of the key link in notes, list all parts in the main notes, and
keep stable keys. Count main scripts separately from supporting records. Saving
notes does not add a script to Library: use save_script
only when actually exposed and its own confirmation contract is satisfied.

Writes are per record, not an atomic batch. After each successful save retain the
key/revision. Reconcile conflicts by rereading; reuse successful records after a
partial failure. Read back saved items in pages of at most five, following revision
cursors, and verify text and goal/source links. Report any partial save precisely.
Do not claim success from a planned write or delete another week's records.

Return a compact seven-day overview plus the first shoot-ready script and batch
checklist; identify where the complete saved scripts reside. If the user requested
all scripts in chat, provide them. A downloadable file is optional when helpful;
do not substitute a transient file for persistent RH notes.

## Resume and learn

For “what should I film today?” read the saved week and return the best unfinished
item with its complete script and shots. For “filmed it”, record a user-reported
stage change without asserting that footage was uploaded. After an actual upload,
link its returned material/project IDs. Move to editing/ready/published only with
the matching evidence; a saved note is not a render or publication receipt.

Before new recommendations, compare relevant dated outcomes with their evidence
and comparable periods. Keep missing owner analytics unavailable. Never turn
your own draft into a performance observation. With no real outcomes, propose a
specific experiment and a later measurement; do not write invented metrics.
Continue paid preparation/rendering/publishing only through real exposed tools
and their exact quote/consent contracts. No scheduler, comment/DM handling or
background delivery is added by this workflow.
