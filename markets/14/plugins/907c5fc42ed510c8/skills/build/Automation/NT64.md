## Reproduce the customer flow

Use one exact Build_ installation throughout a fresh conversation. Select it from
the @ menu with the welcome, idea, approval and report-feedback prompts. Untagged
follow-ups may use context, but the demonstrated release flow does not depend on
persistent automatic routing. A mere chip selection is not a submitted request.

Agree and build a session-only counter. Obtain its complete original-engine ZIP.
On Windows, exercise the controls and preserve the resulting LogReport before
reopening, because the latest launch replaces it. Then visually check reopening at
zero. Return the real report and exact app ZIP for read-only review. A fresh-chat
variant verifies recovery from those same artifacts. Request a next app change only
when the user actually wants one; a clean log is not approval or proof of all features.

MCP guide failure and unavailable GUI test facilities do not gate local delivery.
Actual missing resources, broken code or damaged output still require repair or a
precise limitation. Keep native interaction, local tests and prior-version evidence
separate. Main-app action observations are status-only, with no customer values.

## Prepare, then submit

The package includes five positive and three negative review cases. The actual demo
recording URL is still absent; a script or transcript does not fill that field.
Omitted countries preserve saved Portal targeting, not a new global-release choice.
Verify the existing publisher, countries, connection/domain checks, scans and owner
attestations before submission. No reviewer credentials belong in the public ZIP.

Only an explicitly authorized final submission/publication changes the public state.
The package check BAT performs local checks and does not deploy or submit anything.
Keep owner release procedures out of ordinary customer app conversations.
