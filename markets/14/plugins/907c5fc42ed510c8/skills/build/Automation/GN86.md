# GN86 — Lifecycle and honest test evidence

## Normal delivery and optional qualification

The normal Build_ output is a complete Windows-testable ZIP. Engine static checks,
archive audit, original runtime files and truthful evidence remain required.
An unavailable host display or native Windows runtime is recorded as not_run and
does not stop that delivery. `deliver.py --mode windows-testable` exports the
intact engine archive with `status=delivered_for_windows_test`; it does not invent
runtime qualification or RC18.

Use useful checks suited to the actual app. Small applications need not implement
the full qualification harness just to provide the next prototype. Full
`--mode qualified --allow-execute` execution is optional additional evidence and
uses the stricter plan below when chosen. Never describe unrun checks as passed.
Fix actual source/runtime defects instead of relabelling them unavailable.

## Preserve the original lifecycle and diagnostic contract

The engine copies `iteration/lifecycle_template.py` to
`PROGRAM/Automation/RT42.py` and `runner_template.py` to ZP90.py. Do not replace
either or create a competing LogReport schema. Generated application code may use:

`from Automation.RT42 import ready, fail, case, observe`

Call `ready()` after the actual startup path is usable. A GUI must construct its
widgets/data and process the initial render. A CLI should perform its actual selected
command or produce valid help output. A local server should be listening and responding.
Do not signal readiness at import merely to satisfy a check.

On a handled blocking error, call `fail('stable-code')`, retain a safe diagnostic and
exit nonzero. Do not expose customer values or secrets in reason codes. Normal input
validation stays in the UI and preserves valid state. Unexpected Tk callback errors
remain failures and are captured by the original supervisor. Other frameworks need
appropriate forwarding where the existing hooks do not apply.

Without readiness, a zero exit is startup_unconfirmed, not functional success.
A later ready signal cannot erase an earlier failure. Logs distinguish readiness,
startup/runtime failure, an unfinished snapshot and user-stopped sessions.

Use `observe('fixed-label', 'category', result)` only after checking the real
app-visible outcome. Result is a boolean; labels contain no customer values. A clean
report without button/persistence observations does not prove those features worked.

The launch chain is `run.bat -> ZP90.py -> main.py`. The supervisor writes
LogReport.zip beside run.bat; nothing uploads automatically. Do not claim a report
exists when saving failed or direct the user to a stale report. These mechanisms
are diagnostic evidence, not signatures, a security boundary or user acceptance.

## Available tests for ordinary Windows-testable delivery

Run the engine's syntax/entrypoint checks and archive audit. Check primary logic with
real assertions when feasible. Exercise the actual GUI if a supported display is
already usable; a mock of Tk is not evidence of real window rendering.

No display prerequisite gate is required before implementing the app. Do not launch
an open-ended display setup task. When GUI checks cannot run, record their specific
reason through `iteration_report` with outcome `not_run` before packaging and pass
the same factual limitation to `--unverified-reason` on delivery.

An actual failed assertion, known crash, missing dependency in the delivered package,
or damaged output remains a defect to repair. Preserve the exact evidence. A failed
qualification cannot be converted into a passing or unperformed result by changing
labels or deleting reports.

Use disposable data for tests. For persistent apps preserve the real data identity,
back up before supported migrations and test with actual prior-version fixtures when
available. Do not invent databases/migrations for stateless apps. Verify required
Windows-native assets exist; unavailable target execution remains explicitly untested.

## Optional structured qualification plan

The rest of this guide applies only when full runtime qualification is selected.
Create a host JSON argument file and save it with the CLI plan command; do not
handwrite the protected QA27 record. Example shape:

```json
{
  "schema": "iteration.check-plan/1",
  "kind": "cli",
  "features": [],
  "continuation": false,
  "cases": [
    {"id":"open","phase":"startup","category":"startup","description":"Execute the actual command and assert its output."},
    {"id":"valid","phase":"regression","category":"primary","description":"Exercise the requested action and assert the exact result."},
    {"id":"invalid","phase":"regression","category":"invalid-input","description":"Reject malformed input without changing valid state."},
    {"id":"limit","phase":"regression","category":"boundary","description":"Exercise the actual representation limits."}
  ]
}
```

This is a schema example, not a universal CLI template. Choose kind from gui, cli,
local-web, game or library. Features may be persistent-data, writes-files,
backup-restore, network or native. Choose only applicable features. Use 2–128
unique lowercase case IDs with descriptions of actual assertions.

The strict plan requires startup and primary. Invalid-input and boundary need real
tests or a genuine `not_applicable` explanation of 25–1000 characters each.
Feature-derived categories are required only for their declared features:

- persistent-data: persistence, startup-refusal; a genuine continuation also upgrade.
- writes-files: file-safety.
- backup-restore: collision-recovery.
- network: integrations, normally using local mocks.
- native: native-dependencies.

A persistent continuation supplies the real `previous_archive_sha256` and
`prior_fixtures` paths beneath PROGRAM/ with their hashes. Generate fixtures from
the actual previous source using isolated data. Pass the actual prior archive to
deliver.py; never substitute an invented legacy format or live customer data.

## Optional qualification test execution

The actual entrypoint implements `--iteration-smoke-test` and
`--iteration-self-test`. Use ITERATION_TEST_DATA_DIR for all test writes before
consulting normal data-path settings. Each phase receives independent extracted
bytes and isolated data/config/cache/temp paths. Do not mutate shipped source.

Wrap genuine assertions in `with case('case-id', 'category'):`. Only after the
entire appropriate phase passes print ITERATION_SMOKE_OK or ITERATION_SELF_TEST_OK.
Missing/skipped/failed cases or empty marker-only bodies do not establish
qualification. Caught assertions remain failures. GUI checks must render and
interact with the real interface on an available display.

When testing startup refusal, drive actual initialization against malformed disposable
state, inspect the supervised failure and ensure the input remains intact. Use
timeouts and cleanup. Test collisions/recovery for file-writing and backup features
only when those features exist. Run no test against live records or real credentials.

## Qualification identity

The optional qualified path runs the candidate, creates an observed preflight RC18
receipt, freezes the final ZIP, then executes the exact final archive again.
Only real success writes its qualified output and exact archive hash. RC18 binds
the payload and relevant manifest fields; it is not a ZIP self-hash or signature.

The original candidate is retained. Later bytes must match their evidence.
Linux GUI execution is not native Windows execution. A complete Windows-testable
delivery can have no RC18 and still meet the normal delivery contract.
