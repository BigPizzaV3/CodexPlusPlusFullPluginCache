# CT90 — Bounded Build_ workflow guide

Plugin release: 0.8.10. Compatible server guide: 0.8.10-preview.1.
The server guide version is independent of this installed package's delivery policy.
It supplies an ordinary reminder and resource map, not a build service or host mode.

## One phase-only call

For a relevant submitted Build_ request, call the existing `get_build_workflow`
once with only the phase matching the actual request:

| Request | Phase |
| --- | --- |
| Submitted standalone Press Enter to begin/start or explicit welcome | welcome |
| App idea, requirements answer or prototype discussion | explore |
| Direct instruction or clear approval to build/change the app | build |
| Read-only review or returned-report analysis | review |

A phase describes intent; it grants no permission. Reuse a result already returned
in THIS turn, including by onboarding. Do not duplicate calls through delegation,
replay an old receipt as new evidence or automatically retry failures.

Setup events, blank messages, chip-only selection, pure help, unrelated topics,
quoted requests and opt-out make no guide call. A request solely to upload prompts,
source, files, logs, secrets or project records, or execute/build on the gateway,
is unsupported and makes no MCP call. Classify it before making the guide call.
Send no private material or project identifier through the phase field.

## Follow the current installed workflow

The compatible response has `status=workflow_ready`,
`workflow_version=0.8.10-preview.1`, `source=ordinary_mcp_tool_result` and a public
receipt beginning `bfw_`. A receipt identifies that tool result only. It is not
proof of engine execution, context transfer or future native selection.

Read or retain the complete installed main Build_ skill and its required resources.
Use the actual conversation and latest app archive for requirements and source.
The generic guide does not replace them. Preserve session-only or persistent
behaviour as requested; do not import features from remembered example apps.

For authorized work, use RA89/EX89 to prepare the actual bundled engine and NK24/GN86
to build and deliver. The current normal path is `--mode windows-testable`. It checks
source, archive integrity and original runtime bytes, then exports the complete
engine ZIP. Missing GUI/native Windows execution is recorded as `not_run`, with
an honest delivery limitation. It does not require a separate WIP request.

The server guide's generic reference to required validation, qualification and
delivery gates follows the mode selected by this installed skill. Full application
execution and its RC18 receipt are required only for `--mode qualified`. They are
optional additional evidence, not a universal GUI prerequisite for the normal
Windows-testable path. Never claim qualification that did not run or convert an
observed failure into an unperformed check. Known app/archive defects need repair.

## Availability and boundaries

If the guide is unavailable, fails or is incompatible, state the actual limitation
once and continue through the complete local skill. Do not reopen a context panel,
request hidden markers, prescribe Refresh context, reconnect accounts or substitute
the dependency checker. Server availability does not control local ZIP production.

If actual engine resources or Python execution cannot be obtained after RA89's
bounded procedure, report that precise missing capability. A missing display is
handled by the normal Windows-testable path. Do not replace the engine with a
hand-written launcher or incompatible diagnostic format.

An unrelated topic pauses Build_; opt-out ends it until the user returns. Never
force all messages through MCP. The host selects skills/tools each turn, and a
successful call now does not guarantee later routing. Ordinary use needs no
context-probe experiments, automatic messages or composer manipulation.

Use actual engine results and archive evidence to assess delivery. Local tests,
account updates and receipts do not establish native ChatGPT activation or Windows
execution. Nothing is uploaded automatically; the user chooses which logs to share.
