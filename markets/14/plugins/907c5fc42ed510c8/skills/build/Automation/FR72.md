# FR72 — Build, test, improve, continue

The customer describes an app or change, receives one complete Build_ ZIP, extracts
it, runs run.bat, and returns LogReport.zip with observations. Keep this cycle moving
without making the customer troubleshoot packaging or an unavailable host display.

## Intent

- An app idea remains exploration when the user asks to agree first. Summarize the
  first prototype and ask once whether to build it.
- A direct build request or clear approval authorizes implementation and the next ZIP.
- A review-only request stays read-only. Match report/build identity and explain the
  actual observations and missing evidence.
- An improvement or authorized defect repair resumes the same app and preserves its
  source, data identity, assets and locked decisions.
- In a fresh chat, import the latest actual program ZIP before asking for a rebrief.
  A report alone cannot reconstruct source; ask for the matching ZIP if absent.
- A clean log does not accept a build or authorize new features.

## Complete output

Deliver exactly run.bat and PROGRAM/ at ZIP root. The original engine creates its
launcher, supervisor, lifecycle helper, PROGRAM/readme.md and neutral Automation
records. Keep useful current context: intent, changed/completed/remaining work,
architecture, locked constraints, actual tests, risks and next direction.

Use the normal Windows-testable delivery path in NK24. Missing GUI/Windows execution
is recorded as unverified, without withholding an otherwise complete checked build.
Actual defects require repair. Full runtime qualification is optional; claim it only
when its genuine execution passed. Do not substitute a handmade diagnostic protocol.

## Feedback and handoff

The program ZIP carries source and continuation context. LogReport.zip carries
bounded runtime evidence; it is not source, a data backup or proof of approval.
Reports are local until the user chooses to attach them.

For a new chat, instruct the user to select this same Build_ plugin, attach the latest
program ZIP and describe the next change. Recover the existing app rather than
starting a duplicate. Never claim automatic chat creation, permanent chip selection,
precise context-meter access or model switching.

Keep replies about the app, its testable download and actual evidence. Native Windows
testing remains distinct from checks performed in a Linux chat environment.
