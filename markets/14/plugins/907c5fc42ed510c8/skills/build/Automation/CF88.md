# CF88 — Focused native workflow checks

This MCP-backed version requests the next complete Windows-testable ZIP for an
authorized build/change. It preserves the original engine and diagnostic protocol.
A selected skill invokes instructions/resources; it does not guarantee executable
mounts, automatically intercept later prompts or create a permanent host mode.

## Representative requests

1. Select this Build_ plugin and submit Press Enter to begin: one bounded welcome
   guide call and the brief introduction; no project or app creation.
2. Select the same plugin with a small app idea and ask to agree before building:
   proposal only, correct constraints retained.
3. Select the same plugin with Yes, build it: prepare the real engine, implement,
   perform available proportionate checks, and attach one Windows-testable ZIP.
4. Repeat a relevant follow-up without another mention: continue the actual scope
   when the host selects the workflow; do not claim guaranteed implicit routing.
5. Return a matching LogReport.zip for review: correlate it and explain its real
   observations; respect a read-only request.
6. Request a bounded change: resume the same source and deliver its next ZIP.
7. Ask an unrelated question or opt out: do not build or route through this workflow.

## Evidence that matters

Inspect actual skill/resource reads, engine commands and returned artifacts. Verify
the selected entry is this same package, especially when similarly named versions
are installed. A matching footer, plausible response or claimed static pass is not
proof of engine execution.

For a normal delivery, require the actual delivered_for_windows_test result,
matching exported SHA-256, exactly run.bat and PROGRAM/ at root, original runtime
files, coded context and the original LogReport protocol. Unavailable GUI/platform
checks must be stated as unverified. No display must not force an otherwise complete
app into a withheld ZIP or a demand that the customer request WIP.

Known application failures, missing required files and corrupt output still require
repair. Optional qualified delivery needs its genuine passed evidence and receipt.
Do not fabricate receipts, silently reclassify failed checks or replace the engine.

One successful native app delivery is evidence for that run. Do not claim it proves
all future routing, every host's capabilities or native Windows behaviour. Public
readiness requires representative successful use, not repeated context probes or
a local-only test labelled native.

## Small MCP boundary check

The guide receives only the appropriate bounded phase, once per relevant turn.
Use a controlled unavailable-guide result in an internal integration trial and
confirm the same complete local build path still delivers the ZIP. Do not disable
the live service or make the customer diagnose it. A standard-library counter
needs no dependency lookup. Server success is not evidence of engine execution.

Public and native checks use this one package identity, berrer-build-mcp. Do not
switch to a similarly named older skill between welcome, approval and feedback.
