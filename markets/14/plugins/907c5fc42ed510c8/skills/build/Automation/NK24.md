# NK24 — Practical production sequence

Use the real paths returned by RA89. One session-owned STATE sits outside runtime,
source and output. This package runs inside the chat, not on an MCP build server.

## Start from the actual request

Welcome/help reads the relevant small guide and does not initialize engine state.
An exploratory proposal remains discussion until approved. A direct build request or
clear approval of the agreed prototype proceeds without another confirmation.

For continuation, inspect/import the actual prior program ZIP if it is not already
registered. Recover source, constraints, data identity and the requested change.
Do not duplicate the app or mistake a clean log for acceptance.

## Build and deliver

1. Prepare/reuse the verified engine through RA89. Missing mounts alone do not block.
2. Create/resume the correct project; begin one bounded task using returned IDs and
   live revisions. Preserve the user's locked decisions and existing source/assets.
3. Write complete source under PROGRAM/. Save it using the CLI; the engine generates
   its protected launcher, README and Automation records. Application code imports
   the original Automation.RT42 lifecycle API after packaging.
4. Run `iteration_check` for static source checks. Fix actual defects. Run useful
   host tests that are available and proportionate to the requested change.
5. Save actual test reports with `iteration_report`. Use `not_run` plus the real
   reason for unavailable GUI/platform checks. Do not record an unavailable display
   as a failed application assertion. Preserve and resolve genuine failures.
6. Call `iteration_package` with concrete summary, completed, remaining, what_to_test,
   architecture, constraints and next-direction information. It creates a complete
   immutable original-engine archive; it does not itself establish runtime execution.
7. Export it through the prepared delivery entrypoint:

   `python DELIVER.py --state STATE --build-id ID --output NEW.zip --mode windows-testable --unverified-reason "Native Windows launch has not been run in this host."`

   Add another `--unverified-reason` if GUI interaction or another specific check
   could not run. At least one reason is required for an unqualified archive.
   Require `status=delivered_for_windows_test`, `output_written=true`, and the
   returned path/hash. This nonexecuting path needs no `--allow-execute`.
8. Attach exactly that one ZIP with concise launch and test instructions. Do not
   add files or re-ZIP after export. A missing GUI display is a disclosed limitation,
   not a reason to withhold this complete Windows-testable build.

A known syntax error, missing file or actual application failure requires repair.
Do not send a blocked export, overwrite another file or call unperformed checks passed.
The customer should test the program, not troubleshoot the packaging process.

## Optional full qualification

When useful and supported, configure a request-derived check plan using GN86 and run:

`python DELIVER.py --state STATE --build-id ID --output NEW.zip --mode qualified --allow-execute`

This path executes application tests, freezes a real portable receipt, and executes
the exact final archive. Only its actual `status=passed` establishes that qualification.
Use the real preceding archive for a persistent upgrade where required. It remains
additional evidence; it is not a universal condition for Windows-testable delivery.
Do not attempt GUI qualification merely to rediscover a known unavailable display.
A recorded failed qualification must be investigated, not silently bypassed.

## Engine command reference

The CLI takes `--state STATE` before the command. Read `scripts/iteration/mcp.py`
for exact local action schemas; its legacy name does not declare a remote connection.

- `status`, `projects`: inspect current state.
- `call TOOL --arguments FILE.json`: use actual schema fields in a JSON argument file.
- `import ACTUAL.zip --name NAME`: inspect/import source without executing it.
- `log ACTUAL_LogReport.zip`: match and parse the original diagnostic protocol.
- `checkout --project-id ID --snapshot-id ID --output EMPTY_DIR`: recover editable source.
- `save --task-id ID --revision N --source DIR`: save complete PROGRAM/... files;
  omissions do not delete previous files.
- `plan --task-id ID --revision N --file PLAN.json`: optional qualification plan.
- `export --build-id ID --output NEW.zip`: retrieve archive bytes; use deliver.py
  for the checked customer delivery outcome and its evidence.
- `audit ACTUAL.zip`: static archive inspection, without a runtime/Windows claim.

Host reports are factual descriptions of commands actually run. They remain reported
evidence tied to the current source digest; changed source makes old reports stale.
Use the revision returned by every mutating action for the next operation.

## Baselines and fresh chats

A delivered Windows-testable build, qualified release, imported archive or accepted
build may be an external baseline. Internal retries are different from user upgrades.
Do not invent prior fixtures for a first stateless app. A genuine persistent upgrade
retains the real previous archive and data format.

The complete program ZIP is the portable source/context carrier. LogReport.zip is
diagnostic evidence and cannot replace it. No chat creation, automatic account memory,
native Windows run or model change is implied by packaging or export.
