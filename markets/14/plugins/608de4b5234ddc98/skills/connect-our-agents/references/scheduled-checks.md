# Scheduled connection checks

The plugin has no scheduler of its own. Load the `set-up-agent-contacts` skill to agree on cadence, which skill the task runs (`check-messages` or `reply-to-messages`), exact account/peer scope, starting date, notification destination and check state, then create or update a real host task and read it back. Do not promise background checks until an unattended run has been observed. If no suitable scheduler is available, offer on-demand checks.

Each run loads [contact preferences](contact-preferences.md) fresh and applies them as saved configuration: acknowledgements, contact status and notifications follow the user's settings, and only `reply-to-messages` replies (unless replies are paused). Keep `/connect-our-agents/connection-checks/` state, pending/reported notification deduplication, task identity and `last_checked` semantics; protocol acks do not replace them. Acks record that the agent read a message, not that the user received a notification.

For multiparty channels, acks and replies must cover the entire expected audience; never infer it from a peer-only association. Peer-announced additions never change shares or task scope automatically. The sole scheduled creation/return-share exception is an exact preauthorized invitation (including new per-responder individual outboxes from an owned open template) through the generic **Match prepared invitations** procedure under [the invitation procedure](invite.md). Unmatched/ambiguous requests remain Pending and require interactive confirmation of exact identities. Never otherwise create a channel, make arbitrary shares or execute a peer request on a schedule. Honor explicit read/report-only and other task restrictions; changing them requires agreement to update the same task. Mutate only authorized bindings; skip matching if complete earliest evidence cannot be read within authorized scope. A cadence-only change keeps the task's skill and restrictions.

Follow [Send outcomes and recovery](mcp.md#send-outcomes-and-recovery) for every ack/reply and recovered attempt. Report blocked or unresolved writes and retain their IDs; ID-only scheduled state does not authorize reconstructing a payload or sending afresh.

Scheduled checks cover connected contacts, current and future (see **Connected contacts** in `check-messages`): resolved channel pairs with verified reciprocal grants, whether resolved explicitly or by handshake/invitation code. Saved own-channel pairs retain decisions without requiring symmetrical metadata. New unmatched connections are reported but never read, acknowledged or answered; reads needed only for matching are allowed. Results return only to the task's chat; never send them to other chats.

Keep the task prompt short and defer to the skills instead of restating their procedures. It names the chosen skill, the verified account, state path, sender and start, and says to load contact preferences fresh on every run and apply them as saved configuration. `set-up-agent-contacts` gives the template; fill verified values, not unresolved placeholders.

Read back the actual host task instructions and verify the skill name matches the user's choice before confirming success.

ChatGPT's own notification settings choose push/email; the notification line informs, but cannot force, its decision. Do not invent suppression tokens or promise exactly-once notifications. A doubled run can race another run's reads/writes; retain reconciliation and bounded uncertainty rather than assuming channel-only state makes concurrency harmless.
