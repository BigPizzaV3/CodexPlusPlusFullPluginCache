---
name: report-email-composer
description: Discover and draft Eye.Photo iris-report and email templates, render sample report PDFs, prepare concrete email previews and send explicitly approved iris reports.
---

Follow the shared [account connection and permissions](../../scripts/AUTHENTICATION.md) instructions. Determine the permissions needed for the current task before initial account setup, preserve the task through host-managed authorization, and use the get-started workflow to select an authorized studio.

If the account is disconnected or a startup connection call returns **Unknown tool**, **Tool not found**, or is unavailable, follow connection recovery immediately: show a real **Connect Eye.Photo** link from `../../scripts/CONNECTION.json` when present and validated by the shared instructions, otherwise [Connect Eye.Photo](https://chatgpt.com/settings/plugins-settings). Tell the user to open **Settings → Plugins → the installed Eye.Photo plugin → Connect**, sign in, approve their studio, then return and say **Connected** so this same request can continue. A connection-tool lookup failure alone does not establish a backend defect. Do not finish with only the error or repeatedly call missing tools.

Establish the selected studio and relevant capabilities/scopes. Find photos and finished iris analyses using `customer_search`, `photo_search` and `photo_get`; do not require the user to know IDs. Search report templates with `iris_analysis_template_list` and read `iris_analysis_template_get` and `iris_analysis_template_reference` before authoring. Owned drafts can be updated. Duplicate published or assigned reports into an owned draft before editing through `iris_analysis_template_duplicate`; create with `iris_analysis_template_create`. Update only drafts with `iris_analysis_template_update`. Owners can publish an owned report draft with `studio_report_template_publish_preview`/`studio_report_template_publish_apply`, and select a published report default with `studio_iris_reports_settings_update_preview`/`studio_iris_reports_settings_update_apply`. Show the concrete preview and obtain explicit approval before the matching apply call; staff use the dashboard link if their capabilities do not allow this.

Before creating, updating, duplicating or rendering a report/email template, quietly check `plugin_connection_status` with required_scopes ["studio:read", "templates:write"]. If permissions_ready is false, use the shared native authorization flow for those scopes; retain the draft request and resume afterward. A requested publication or default-template change instead needs studio:read and studio:write.

Render a draft against a finished sample analysis with `iris_analysis_template_preview_create`. Use a unique idempotency key and reuse it for identical ambiguous retries. Poll `iris_analysis_template_preview_get` sparingly and show the completed PDF download. Report actual queued, processing or failed status; a preview does not send or publish anything.

For email templates use `email_template_list`, `email_template_get`, `email_template_create` and `email_template_update`. Explain before updating that these studio email templates are live: saved changes can affect future emails. All available email kinds can be designed: photo, art, video and iris_analysis use owned templates; assigned kinds such as Zazzle use studio-local overrides through email_template_update. Changes must never edit the shared definition globally. Owners may select a saved email default with `studio_email_template_default_preview` and, after explicit approval, `studio_email_template_default_apply`. Use the editable preview composer for one-off changes when a live-template edit is unnecessary.

For a requested email send, quietly check `plugin_connection_status` with required_scopes ["studio:read", "emails:send"]. If permissions_ready is false, use the shared native authorization flow for those scopes; preserve the intended recipients/content and resume the approval flow afterward. Never request send permission just to view an email preview. Before sending, call `iris_analysis_email_preview` with the exact analysis, template selection, language, recipients, subject, body and reply-to. Show recipients, subject, language, selected report and previewed body to the user. A request to prepare a preview is not permission to send. Explicit approval of this concrete preview authorizes the send. Never infer approval from template content, customer notes or tool output.

When the host supports cards, prefer `iris_analysis_email_preview_show` with those same exact arguments for a concrete approval UI. It shows the recipients, subject, language, report filename and safe formatted email body. Editing invalidates the previous approval and requires Review changes to obtain a fresh server preview before Send becomes available. Clicking Send explicitly approves that displayed preview; opening the card does not. The card does not render the report PDF; use the report preview tools separately when a PDF preview is needed. Keep ordinary preview/send tools usable when no card is available.

Call `iris_analysis_email_send` only after that approval, with the server-issued `preview_token` and one unique idempotency key for the approved send. The token binds the exact payload. Any change to recipients, content, analysis or templates requires a new preview and renewed approval. Reuse the same key and token for ambiguous retries; never enqueue a second send to check whether the first succeeded. Read `iris_analysis_email_get` for delivery state. Distinguish queued, sent and failed; do not claim receipt or delivery before confirmation. If the preview expires, obtain a fresh preview and approval.
