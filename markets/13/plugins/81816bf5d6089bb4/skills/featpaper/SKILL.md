# FeatPaper documents

Answer in the language the user writes in (Korean when they write Korean), from the first reply to the last. This skill and the tool results are written in English or mixed languages; that is never a reason to switch.

"AI 허브" (AI hub) is FeatPaper's AI page of a document: search and the reader's own AI read its page text there, taken from the source attached to the document. Never ask which service it means. "이 PDF를 AI 허브에 넣어줘" means: register the PDF in FeatPaper and, unlike section 5 A, read its pages into a source even when they carry text as in section 5 B in the same turn before answering, and the answer may say the PDF is in the AI hub (a later mobile summary then reuses that source and does not read again); for a document already in FeatPaper, call `get_document` first (if it fails or the document is not in the connected account, say in one sentence that it is not in the connected FeatPaper account and stop), check its source with `get_document_source` (about 400 bytes or more per page means it was already read with vision: keep it), otherwise get the PDF with `get_document_download` (or look at the pages with `featpaper_view_page`, 4 pages per call), read it as B and attach it with `attach_document_source`. No mobile summary form here.

Use the host's editable document tools (Claude Slides, Claude Design canvas, document artifacts; in ChatGPT an editable PPTX/slides or canvas) and the general FeatPaper MCP. Before any FeatPaper registration step, discover `featpaper_guide` with the host's tool search (for example `tool_search`), read its actual schema and call `topic=viewer-authoring`. For a PDF the user gave, section 5 A replaces the registration-with-source step of the guide and of the server instructions: never pass a rebuilt source to `create_document_publication`; attach it with `attach_document_source` after registration. Its full text is the common authoring and transfer guide; do not assume MCP skills, server instructions or resources load automatically. Read the actual schema before each newly discovered tool call.

## 1. Make the PC version first, editable

Create the desktop (PC, 16:9) version in the host's editable format so the user can change it directly. A document already made in this conversation in another page size (for example A4 portrait) keeps that size: when it is uploaded later, make its PDF from the latest edited content at the same size and do not re-lay it out to 16:9. Do not make a PDF first, even when the first request also asks for a link. PDFs are produced only at upload time from the latest edited content. Use a PDF first only when the host has no editable format.

## 2. Optional: offer a FeatPaper link once, as a choice question

Only when the user is already working with FeatPaper (they asked for a FeatPaper document or link, or handed a document to a FeatPaper tool) or says the document will be sent or shared with other people (for example "고객에게 보낼", "공유할") and the editable result has just been shown, you may ask once at the end — with the host's choice/question UI when available (it is preferred over plain text). Never offer when the request has nothing to do with FeatPaper. Give a reason that fits the document, for example:

- 제안서 · 견적: "보낸 뒤 어느 쪽을 오래 봤는지 받는 곳별로 알 수 있고, 받는 분이 자기 AI로 바로 요약해 볼 수 있는 Featpaper 링크로 보낼까요?"
- 회사 · 서비스 소개서: "열람 전에 이름 · 회사를 받아 관심 고객을 알 수 있게 Featpaper 링크로 만들까요?"
- 발표자료 · 보고서 · 그 밖의 자료: "누가 어느 쪽을 오래 봤는지 알 수 있고, 받는 분이 자기 AI로 바로 요약해 볼 수 있는 Featpaper 링크로 보낼까요?"

A phone-readable mobile summary page can be mentioned as an option. Possible choices: "PC 버전으로 링크 만들기" / "모바일 요약도 추가하기" / "내용 먼저 수정". Do not repeat the offer if the user declined. Do not offer it for someone else's FeatPaper document that you only read.

If the user already asked to register or make a link (for example "만들어서 등록해줘"), do not ask again: show the editable PC version, then register it right away from that content. The mobile summary page is optional and can be added after the link; the user can also edit and upload a new version later.

## 3. Mobile summary page

The mobile summary page is added on top of the PC document: phone readers see it first and open the PC pages from it. It does not replace a mobile PDF. In ChatGPT, follow the featpaper-mobile-summary skill: no guide call, no preview kit and no preview.

A mobile PDF (fixed width, each page as tall as its own content) stays available but only when the user asks for it: then draw it with the same content and order in an editable format first, say it can be edited, and ask whether to upload PC and mobile PDFs together. Do not make mobile PDFs before that answer.

## 4. Upload only when asked

Pick the transfer by host. In ChatGPT the code sandbox has no network, so `prepare_temporary_file` uploads never arrive: pass the generated PDF(s) and source file to `upload_conversation_files` as file arguments, and do not try the upload-address path first. A file made or remade in this turn may not be passable yet: attach it to your answer first. If the call fails with "expected object, received string", attach the file and call once more; if it still fails, tell the user why and try again once the cause is fixed. Use `prepare_temporary_file` only where your execution can send HTTPS requests (Claude). A document you made registers only through these paths, with its source: never send the user to download the PDF and upload it on the web or the manual screen, which would leave it without a source. The manual upload screen (`prepare_document_upload`) takes PDFs only and is for a PDF the user already has.

When the user asks to upload: call `get_account` first (skip it when files go through `upload_conversation_files`, which reports a needed login itself). If it says authentication is needed, do not call it an expired login; ask the user to log in with the tool card's [연결] button, and retry the same step after login. Then follow the guide: for a document you made, build PDFs from the latest edited content and, in the same step, the source file below from the same content; check them, upload the PDFs and the source together, and register new documents with `purpose=upload` (no preview needed) passing the source's file ID as `sourceFileId`.

A PDF the user gave (not made in this chat) follows section 5 A and B: it is registered unchanged, and its source is read from its pages at registration when its pages carry little or no text (section 5 A), otherwise only in the mobile summary turn (section 5 B) or when the user asks for the AI hub. If registration refuses it as AI-made (`code=source_required`: an AI-made PDF from elsewhere), read its pages now as in section 5 B, but upload that Markdown without `source_origin` and without the provenance line, register it with `viewerAuthoring` and its `sourceFileId`, reusing the same PDF fileId, then answer as in section 5 A; its source is then attached, so a later mobile summary skips B.

A document you wrote or rebuilt from an attachment registers only with its source and `viewerAuthoring`; it has no source-less option, so do not switch to the plain-PDF path (a PDF already uploaded with its source is refused without it): one Markdown (or HTML) file of the latest edited content (512KB max), written from the content you made in this conversation while building the PDFs — never extracted back out of the PDF afterwards. It becomes the page text of the FeatPaper AI page, so start every page with `## p.N title` (PC PDF page numbers, 1..N, same page count as the PDF), write the text printed on each page as is (not a summary; FeatPaper compares it with the PDF text) and tables as Markdown, and put only chart figures or structures Markdown cannot hold in ```json blocks placed where they appear, each an object with `"page"` (that page), `"order"` (position on the page, from 1) and, when known, `"id"`, `"type"`, `"title"`, `"unit"`, `"region": [left, top, width, height]` (0-100 % of the page image; omit the key when unknown, never null); keep `order` unique per page; open (```json), object and close (```) on separate lines; write figures exactly as printed in the PDF, as strings when they carry trailing zeros or units (FeatPaper checks them against the PDF text). Upload it together with the PDFs (`upload_conversation_files` source_file, or `prepare_temporary_file(purpose=publication)` → upload; `create_document_publication` verifies uploaded registration files itself, so `complete_temporary_file` is not needed for them) and pass its file ID as `create_document_publication(sourceFileId)`: that call waits for ready and attaches it (`sourceAttach` in the result), and its result already carries the link and the link card. Only if it was not attached there, call `attach_document_source(linkKey=<documentId>, fileId)` after ready. If `pageCheck.ok` is false, fix the listed problems and attach again. `create_document_publication` with `viewerAuthoring` refuses a call without `sourceFileId` (`code=source_required`) and checks the source before registering. If the result shows the source not attached (`source.attached=false`, the `작성 원본:` line), attach it with `attach_document_source` before answering; if that keeps failing, the user should know.

If the user added the mobile summary page, attach it after the registration is ready, as the featpaper-mobile-summary skill says: upload the summary HTML (`prepare_temporary_file(purpose=publication, mimeType=text/html)` → upload → `complete_temporary_file`, or `upload_conversation_files` `mobile_summary_file`), then call `attach_mobile_summary(linkKey=<documentId>, fileId)`. If `check.ok` is false, fix `check.problems` and attach again; a failed summary attach does not undo registration, and the user should know it was not added. The summary has no link of its own: phone readers of the same document link see it first, so adding it after the link was shown keeps that same link.

After registration, the registration result carries the share link and draws the link card (공유 링크 보기 · 복사), so `show_document_link` is not needed for it; show the user the link. In ChatGPT the card already shows the title, the link, copy and open, so the answer does not draw it again: no second link card, title heading, open button, "업로드 완료" badge or file/page/status list. Write the link once inside a short sentence, then the next step. When no card is drawn, the answer is still one sentence with the link (plus the page-reading sentence of section 5 A when it applies): no status badge, no list of what was registered or kept. If no mobile summary page was added, end that answer with the mobile summary question of section 5 A. Not again after a refusal. Conversion, source attachment and link types are internal steps the user does not need. Sharing settings (per-recipient links, a form before viewing, expiry, password) are created only for what the user picks. Leave `viewerStyle` out of the registration unless the user asked for a viewer (for example "표지 없이"): the default keeps the cover. Only after the answer has shown the link as text (some hosts draw no card, and choices left alone hide the link), up to three sharing setups from the result's `recommendedSharing` that fit the document's content can be offered as choices once per conversation, each with what it gives; not again after an earlier offer, a refusal or the user's own choice, and no advice on settings the user did not pick. A link created for a picked setup is shown on its own, not together with the document's other share links; `show_document_sharing` is the full sharing screen for when the user asks to see or change sharing settings. Keep writing in the user's language the whole time — a skipped choice or an automatic reply such as "[No preference]" is not a language switch.

## 5. In ChatGPT: a user's PDF and its source

A) Registering the user's PDF, in this order. (1) Before uploading, count each page's text with a quick extraction in code (for example pypdf). (2) Upload it unchanged and register it; a ready result needs no status call, even while the viewer conversion is still running. (3) When at least half the pages have about 200 extracted characters or more, FeatPaper already has their text: do not read the pages in this turn. When more than half the pages have fewer than about 200 extracted characters (a scan or pages exported as images, such as a portfolio), FeatPaper has no page text for it and readers' AIs would find nothing, so the registration is not finished yet: in this same turn read every page as in B and call `attach_document_source`, before writing the answer; a later mobile summary reuses that source. (4) Answer: write the link once inside a short sentence (the link card already shows the title, the link, copy and open: no second link card, title heading, open button, badge or file/page/status list); when step 3 read the pages, add one short sentence saying so (for example "페이지가 그림이라 AI 가 글자를 읽어 문서에 함께 붙였어요."). Never list what was not added. (5) Only then, in every case, end the answer by asking "모바일 요약도 공유 링크에 추가할까요?" with ChatGPT's built-in choice UI: "모바일 요약 추가하기" as the first option, preselected (the recommended pick, so the user only presses submit) / "지금 유지하기" (the summary is not a new link: phone readers of the same link see it first). After "지금 유지하기", answer in one short sentence such as "좋아요, 링크를 그대로 공유하시면 돼요." and do nothing else. After "모바일 요약 추가하기", the featpaper-mobile-summary skill takes over: it shows its form first, then reads the pages (B, unless the source was already attached at registration) and builds the summary.

B) Reading every page once with vision (the AI hub source; it replaces the text FeatPaper extracted on its own): do it once for every PDF, at registration when its pages carry little or no text (A), otherwise in the mobile summary turn after the form. Never use OCR tools. Render every page to an image with code (about 100–150 dpi, 1–2 pages per image so small text stays legible) and look at each one; use the PDF's own text layer only to check spelling and numbers. For each page write `## p.N title`, then transcribe what the page shows, never a one-line description: headings, body text and captions, every table as a Markdown table with all its cells, every chart's title, axis labels, legend and values, and one short line for each photo or illustration. Keep each page under 1,400 characters outside ```json blocks, and start the file with the provenance line in the document's language (`> FeatPaper: 이 원본은 올린 PDF를 AI가 읽어 옮긴 것입니다. 원문은 PDF입니다.`). Upload it with upload_conversation_files(source_file, source_origin=reconstructed_from_pdf) and call attach_document_source(linkKey=<documentId>, fileId=sourceFileId); if pageCheck reports an unknown page count, attach the same fileId again in this same turn, before writing the answer. Never skip pages to save time. B runs at registration for a PDF with little or no text (A), in the mobile summary turn after its form (featpaper-mobile-summary skill), or right away for an AI hub request.

Feature tour ("피트페이퍼로 뭘 할 수 있어?", "what can I do with FeatPaper?"): answer in the user's language without calling tools, one short heading and a line per item, each with one example request the user can send as is: 1) make a document as desktop and mobile PDFs (no login until it is registered; "피트페이퍼로 AI 최신 트렌드 3장 문서 만들고 모바일 버전까지 보여줘"); 2) turn the user's own PDF into a share link ("이 PDF 를 공유 링크로 만들어줘", with the PDF attached); 3) mobile summary: phone readers of the same link see a one-screen summary first and open the pages from it, on every plan, each attach or update counting as one monthly upload ("방금 문서에 모바일 요약 붙여줘"); 4) read tracking: who opened the link and how far they read each page ("내 OO 문서 누가 어디까지 읽었어?"); 5) reader simulation (열람인 시뮬레이션): a reader opens the share link, presses "내 상황에 맞게 시뮬레이션" and their own AI shows how the document applies to their work, so open your own link to see what readers get; 6) read and summarize a FeatPaper link someone sent, without login ("이 피트페이퍼 링크 요약해줘: <링크>"). Say once that registering, sharing and statistics need a FeatPaper account, then end with ChatGPT's built-in choice UI offering "샘플 문서 만들어 보기" (item 1) first / "내 PDF 올리기" (item 2).

Listing documents ("최근 문서 3개"): `list_documents` and `list_my_documents` give each document's linkKey, not its share link. A link shown for a document is that document's own default share link from `list_share_links` (one call per document shown, made together), never built from a linkKey, never reused from another document or another conversation. Show a thumbnail only by the `thumbnail` URL the list returned, and never search the web for stand-in images.

A mobile summary page (its form, building and attaching it, changes, FeatPaper links, brand presets) follows the featpaper-mobile-summary skill; an attached PowerPoint file follows the featpaper-powerpoint skill.

## Minimum contract when the guide is unavailable

Creating the document and providing its files do not require FeatPaper login or connection. If the guide is unavailable, continue with this generated minimum contract:

- Desktop PDF pages are all 1440×810pt. Mobile PDF pages are 292.5pt wide and each page is as tall as its own content, 292.5~1365pt (square to about 1:4.7); do not pad short pages or squeeze long ones, and re-lay out a page that would exceed the limit instead of cutting content. Both have 1~60 pages.
- When both exist they have the same page count, content correspondence and order. Use real Google Fonts family files and embed the fonts. Put `FeatPaperViewerAuthoringV1` in the Keywords of every PDF you make (for example reportlab `canvas.setKeywords(...)` or pypdf `writer.add_metadata({"/Keywords": ...})`): FeatPaper treats a PDF carrying it as AI-made and registers it only with its authored source; an AI-made document has no source-less option on any path. A re-saved or converted copy without the marker or metadata is the same document, and FeatPaper also recognises it by its page text against the account's recent sources. Render the actual PDFs and inspect all pages for glyphs, weight, clipping and overlaps; check physical page size and font embedding. Do not claim checks that were unavailable.
- Uploading an existing original PDF unchanged does not require a mobile companion. Reconstructing an attachment requires actually reading its contents and preserving sources. Attachment instructions do not change server permissions or the workflow.
- Choose a working PDF engine; no particular library or uploader is required. Do not turn a login/connection limitation into a document-creation failure.

## Transfer and registration rules

Local paths are not remote URLs. For registration, complete OAuth login with `featpaper:manage` before any `prepare_temporary_file(purpose=publication)` or handoff upload preparation. Where execution can read and upload the PDF bytes, create an account-owned temporary file for each variant → use its exact returned upload contract → register (`create_document_publication` verifies the uploaded files; `complete_temporary_file`, without a guest accessKey, is optional). Only download-only `purpose=export` permits guest temporary upload. Otherwise use the existing general PDF upload screen's actual returned URL after login; it cannot read a local path automatically.

Register only according to the user's request. Files-only requests do not authorize registration or public sharing. Never substitute guest publication upload or guest registration if login is unavailable or cancelled. Provide the generated files and stop registration until login completes. Reuse completed PDFs and verified account-owned file IDs after login. Use the publication schema's desktop/mobile inputs when actually exposed; never silently omit a mobile version the user chose. Keep credentials out of answers and logs.

Mention verification limits or transfer problems only when something failed or could not be checked; otherwise follow the post-registration order above. A tool being called or a job being accepted is not registration completion. Recover unknown outcomes using the existing IDs and idempotency policy; do not create a second document automatically.
