# Record and reconcile an existing payment

Inspect current connected schemas and `grid.get_connection_info`. This skill records past events; never execute a bank transfer, charge an account or use payment initiation tools. It works independently with existing project, payee and payable IDs. For composition use the [checkpoint contract](../process-vendor-invoice/references/checkpoints.md).

Read all relevant pages of `grid.list_project_payables`, `grid.list_project_payments` and, when authorized, `grid.list_transactions`. Inspect selected records through `grid.get_payable`, `grid.get_payment` and `grid.get_transaction`, following nested evidence/application/allocation cursors too. Match canonical payee, project, currency, amount, date, reference and invoice evidence; matching amounts alone do not identify a payment. Search existing partial payments, refunds and applications before proposing another payment. Missing documents or bank imports do not prove unpaid status.

Keep these observations distinct in the report:

- User reports sent: an attributed user statement, not bank confirmation.
- Bank confirms sent: verified execution evidence, not vendor receipt or necessarily a posted imported transaction.
- Vendor acknowledges receipt: vendor evidence, not bank matching.
- Posted bank match: an existing transaction reconciled to the recorded payment.
- Invoice settlement: active payment applications and the canonical remaining balance; neither project allocation nor bank reconciliation substitutes for this.

Read methods from `grid.preview_record_payment` before proposing a record. Zelle records the actual Zelle method; `logged` is neutral bookkeeping with no asserted payment rail. Both only record a past event, never initiate execution. Verify deployed availability: an older build may lack these methods. Never substitute ACH or wire. Reuse existing matching payments; matching active identity/currency/amount/date blocks another record.

If the invoice already has issued PO/Actual details, reuse those IDs and existing invoice evidence. Create only missing AP, link the existing invoice and code the existing details; do not import the costs again. Use `grid.preview_edit_payable` / `grid.apply_edit_payable` with explicit `fields.status: pending_approval` to review needs_review/draft AP, then a separately confirmed `fields.status: approved` decision to approve it. These use canonical AP permission and authenticated audit identity. Do not interpret recording a payment as AP approval. Disputed/void/settled lifecycle corrections remain outside this transition.

For an authorized already-made payment, show evidence strength and exact payee, project, amount, currency, date, method and sanitized reference. A user statement can support a bookkeeping record, but must remain attributed; do not invent bank-confirmed status. Use `grid.preview_record_payment`, with `action: record_payment`, a pre-minted stable `record_id` and supported fields. Review duplicate warnings, proposed changes and balances. Obtain explicit confirmation, then `grid.apply_record_payment` with identical intent, `preview_time`, `expected_revision`, stable `request_id` and `confirm_preview: true`. Read back with `grid.get_payment`. Reuse an existing matching payment rather than recording it again.

Apply existing payment amounts to the correct AP separately with `grid.preview_set_payment_applications` / `grid.apply_set_payment_applications`. Show exact named pairs and before/after applied and outstanding balances, including partial settlement. Omitted pairs remain unchanged; zero reverses a pair with audit history. Obtain confirmation before apply and read both payment and payable afterward. Do not overapply, net unrelated credits or infer zero from a null balance. Paid labels alone are insufficient.

Before choosing a transaction account or requesting an import, inspect deployed schemas for `grid.list_financial_accounts` and `grid.get_financial_account`. Follow `next_cursor` with `after_id` until null, preserving filters. Match the user’s institution, stored display/product name, last four, account type and authorized owner context to the exact Grid `account_id`; inspect the selected ID and compare its identity with sync status/preview. Duplicate labels/masks are separate candidates and require clarification; null/unavailable metadata must remain unknown. Never identify an account by historical amounts. Linked accounts in status are only caller-visible non-deleted accounts, may be paginated, and do not prove the full Item scope is visible.

When an authorized account import is missing, inspect the deployed schemas for `grid.get_account_sync_status`, `grid.preview_account_sync` and `grid.apply_account_sync`. Read status first: last Grid import and Item cooldown are separate from bank/provider freshness, which may be unknown. Only an explicitly requested, previewed and confirmed import may apply with stable request identity. It imports what Plaid already knows across sibling accounts on the same Item; it does not refresh the bank or guarantee immediate posted data. Keep exact request arguments for uncertain retries; processing/unknown and cooldown skipped receipts are not successful syncs. Inspect imported transactions and attribution/backfill warnings before matching; never force, sync all, automatically start a new request, or claim deployed availability without discovery.

For Venmo and similar payment apps, distinguish the vendor payment from a bank funding debit or wallet settlement. Inspect both accounts and selected transactions, including description, provider category, counterparties, allocations and evidence. Two same-signed outflows are not an opposite-sign transfer pair; equal amounts or a Venmo label do not prove funding. Keep one vendor payment and its AP application. Do not create a second cost/payment for a verified funding movement, fabricate a missing wallet leg, or classify an unresolved candidate.

When source evidence identifies an unallocated standalone funding entry, discover `grid.preview_set_transaction_transfer` / `grid.apply_set_transaction_transfer`. Preview `action: set_transaction_transfer`, the authorized project and transaction `record_id`, and `transfer_decision: mark_funding`. Show the exact transaction and evidence, cleared party/project suggestions and warnings, then obtain confirmation and apply with the returned revision/time and stable request ID. Read back the transaction; verify the vendor payment and AP remain separate. Pending, paired, allocated, removed or financially linked candidates require their existing review workflows first. If these tools are absent, report the deployed capability gap; do not use UI/SQL as a substitute. To undo, preview `transfer_decision: restore` with `transfer_source_request_id` from the original successful actor-owned classification receipt. A successful restore consumes that source receipt; redo requires a fresh reviewed classification. Do not use classification to bypass an uncertain or duplicated payment.

Bank reconciliation is another operation. If the posted transaction has not been imported, report reconciliation pending; do not fabricate a transaction, create another payment or mark the invoice unpaid. If it exists, verify native currency, amount, payee and allocation. `grid.preview_set_transaction_allocations` / `grid.apply_set_transaction_allocations` replace the complete allocation set, so preserve unrelated legitimate shares in the reviewed proposal. Preview/confirm that change separately if needed. Use `grid.preview_reconcile_payment` / `grid.apply_reconcile_payment` for the existing payment and explicit transaction only after showing the matching evidence. Read back payment, transaction and AP; the matching operation does not itself apply the payment to an invoice.

For each operation, inspect its current action/input schema and retain exact target, returned revision/time and request identity. Identical uncertain retries reuse the same approved request and receipt contract. Changed balances, intent or expired previews require fresh review and confirmation. Never undo or delete prior successful stages to compensate for a later failure. Return saved IDs and evidence-qualified payment, application and bank-match outcomes independently, with any missing capability or bank import.

Any email requires separate explicit approval for that exact send; financial approvals never authorize an email.
