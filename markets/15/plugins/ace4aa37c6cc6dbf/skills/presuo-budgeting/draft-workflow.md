# Shape and save a budget proposal

Use this workflow when the user is exploring or preparing a **new** budget. A Presuo draft is a resumable working proposal, separate from a regular budget. Checkpoint it as the proposal develops; promotion is a separate action that requires a server-calculated review and the user's explicit approval.

# Core workflow

When creating a new budget or proposal:

1. Do not create categories, line items, measurements, or assumptions immediately.
2. Start with one broad, open-ended question:
   "Tell me what you want to do and what you already know about the project."
3. Continue discovery with a small number of follow-up questions based on the user's answer.
4. Do not invent scope that the user has not supplied unless clearly marked as a suggestion and the user has asked for suggestions.
5. Only save a draft after enough project context has been gathered.


## Shape the proposal

1. **Understand the request.** If the user wants a new proposal but has not described the work, invite an open-ended description: “What work are you planning? Tell me whatever you know so far—even rough notes are fine.” Ask only questions whose answers materially change the scope or the current step. If an existing budget may be intended, clarify before starting a draft. Do not lead with a budget name, category, quantity, currency, or destination question.
2. **Show the evolving proposal.** Use a compact table when there are multiple items, with work item, rough quantity or dimension, and price only when supplied or requested. Include a short status or source when useful. Keep uncertainty explicit (“about 30 m,” “not specified,” “suggested”). Group related work into a few useful sections; do not require the user to provide formal categories. Never silently turn unknown values into zero or a default unit in the conversational proposal. When dealing about a specific work section, and if the draft has too many rows, the table can show only its items of the current section.
3. **Clarify and revise.** Apply corrections directly and state only material changes. Preserve whether details came from the user, an attachment, an assistant suggestion, a calculation, an assumption, or remain unknown. Suggestions are not confirmed scope. Do not ask the user to resolve low-impact unknowns just to make the draft structurally complete.
4. **Checkpoint as the proposal grows.** Once the user has shared substantive scope, call `draftbudget.get` to check for an active saved draft. If an unrelated draft is active, do not write to it; explain the situation and continue shaping the proposal in chat until the user clarifies. Call `draftbudget.save` with the complete desired snapshot to create the first draft (`draft_id` and `base_revision` both `null`) or update the active one with its current ID and revision. Omitted rows are deleted, so preserve every untouched row and its server ID. Batch known changes into one save. Do not ask permission for each checkpoint, but tell the user naturally that Presuo is keeping a resumable draft. Claim it was saved only after Presuo confirms. A request to start a proposal without any scope is not by itself a reason to save.
5. **Validate measurement fields before saving.** Use only a unit grounded in the user's description or source. Populate only fields applicable to that unit: `unit` uses `quantity`; `lm`/`m` use `multiplier` and `length`; `m2` adds `height`; `m3` adds `height` and `width`; `kg` uses `multiplier` and `weight`. Set non-applicable fields to `null`. Use `multiplier: 1` only when the dimensions are supplied and no repetition count was given. Do not infer missing dimensions, quantities, or prices; leave them `null` and mark quantity/price status `unknown` when the corresponding value is unknown. Before calling `draftbudget.save`, check each measurement's unit, applicable fields, status/value pairing, and provenance together. Keep the draft's remaining unknowns visible in the proposal; do not repeatedly rewrite the snapshot to force it into a promotion-ready state.
6. **Keep destination selection at promotion.** A draft checkpoint can remain without a project or currency. Do not call `project.list_accessible` or ask the user to choose a destination while shaping the proposal unless they explicitly ask to link it sooner. When preparing promotion, use `project.list_accessible`, present eligible projects if the destination is not already explicit, and let the user choose. Use supported currencies from `draftbudget.get`'s `creation_context`; select only a currency the user specified or confirmed. Save the chosen project and currency in the complete snapshot. Change an already selected destination or currency only on the user's explicit correction. Never infer currency support from locale or project name.
7. **Handle draft writes safely.** For each save, use the current `draft_id` and `base_revision`, a fresh idempotency key for each distinct operation, and server-issued draft-local IDs. Use returned revisions and snapshots as authoritative. On timeout or a lost response, retry the identical operation with the same key. On conflict, refresh with `draftbudget.get`, inspect the authoritative snapshot and creation context, and reconcile before continuing. Do not invent IDs, category codes, or ordering. Do not narrate these mechanics unless needed to explain a delay or failure.

If `get` or `save` returns `legacy_transformations`, disclose those previously adjusted prices before promotion or changing them. The public snapshot carries the recorded net price without the old transformation metadata. An explicit net-price edit replaces that older transformed value; preserving its price leaves the server's historical metadata intact.

## Review and promote

8. **Review the saved draft.** When asked to review it, call `draftbudget.get` and summarize the persisted structure, including material unknowns. Apply requested corrections. Delete content only when asked.
9. **Review and obtain consent.** When the user wants detailed manual entry, or the proposal is mature enough for the regular workflow, offer to create a regular **In preparation** budget. Never promote solely on the assistant's judgment. Call `draftbudget.get` with `include_promotion_review=true`. Present its authoritative snapshot, destination, blockers, and material defaults, including any unit or numeric zero the server would fill. Explain that promotion creates a regular budget. Ask for explicit approval of the exact result. A review token binds the returned state; it does not prove user approval. A request to review or “leave it as is” is not approval to promote.
10. **Promote only after approval.** After the user explicitly approves, call `draftbudget.promote` with the same draft ID and revision, the review token, and a fresh idempotency key. Do not promote if the review has blockers, the token is stale or expired, or the draft changed. Refresh and review again, then obtain approval again.
11. **Report and hand off accurately.** On `committed` or `already_committed`, confirm that the regular budget was created, provide its returned name, project, and direct URL, and offer the editor handoff when available. Open the editor only through a returned authorized handoff and only after promotion. If the user asks to edit an unpromoted draft, explain that the editor requires a regular budget and offer the promotion step; do not promise to open the editor first. Never claim success based only on a timeout. Retry the same promotion with the same key to recover its receipt; do not use a new key to bypass an uncertain result.
12. **Discard only on request.** Call `draftbudget.discard` only when the user explicitly asks to discard the active uncommitted draft. Confirm the result. Never discard after promotion. If an unrelated active draft exists, do not replace, retarget, or silently discard it; explain that the connection has another draft in progress and continue in chat until the user clarifies what to keep.

## Errors and limits

- Do not surface every validation finding while scope is being assembled. Name and destination requirements become relevant when preparing promotion.
- On `FORBIDDEN` or `NOT_FOUND`, explain the access result without guessing another identity or exposing hidden records.
- On `CONFLICT`, refresh and reconcile. On `STALE_PROPOSAL`, request a fresh promotion review and obtain approval again.
- If a capability is unavailable or Presuo returns an error, explain what could not be completed. Never claim persistence or promotion without tool confirmation.
- Promotion quotas and model capacity are checked at commit. If Presuo reports a capacity limit, explain the reason and next step; the draft remains available.
