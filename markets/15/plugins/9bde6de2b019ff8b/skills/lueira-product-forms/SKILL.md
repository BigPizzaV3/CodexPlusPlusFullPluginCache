---
name: lueira-product-forms
description: Help a Lueira tenant build, review and change the forms customers fill in at checkout, check-in or per participant, and see which products use them.
---

Discover the available Lueira product form tools and read their schemas before choosing an operation. The MCP exposes different tools according to the connected tenant's scopes, so a missing write tool means the connection can only read forms.

A form is an ordered list of reusable sections, and a section holds the questions. The admin calls the section library the "Collection". A section can be shared by several forms: editing it changes every form that uses it. A product can use a form in three slots: checkout (shown in the online store before the purchase is completed), check-in (collects information during check-in or before the activity starts) and participant (shown for each participant during online booking). Products also have a legacy `form_id` slot. Rental products and bundles, group lesson products and packages, private lesson products and courses take form slots; shop and pass products do not. The product update tools accept `"none"` to detach a slot. Answer validity, in days, only matters for check-in forms: a participant's answer is reused until it expires, and a form without validity never expires.

To build a form, first read how questions are written with the question schema tool; do not guess question types or properties. Then read the existing forms and sections and reuse a section when it already matches the request. Create the new sections, create the form with the section IDs in display order, and attach it to a product with the update tool of that product type. Question rules in plain words: radio and select questions need options; a conditional yes/no question (`conditional_radio`) can reveal nested questions, but nested questions cannot be yes/no questions or static text; copying an answer into a customer record is only possible from top-level questions and only to the listed fields; translations use the supported language codes. If the tool refuses a question, read the reason, fix that question and retry; do not drop the validation.

To edit a section, read it first, change the question list and send the complete list back: the questions replace the old ones. Re-send each existing question with its `id` and `key`, because a question sent without them may get a new id, which would detach the answers already stored for it. Before editing a shared section, find the forms that use it (no tool lists them by section, so read each form's `section_ids`) and tell the user that all of them change. To change a section for one form only, create a new section and swap it into that form's `section_ids`; there is no way to unlink a section here.

Before deleting a form, or moving its products to another form, list the products that use it (`list_product_form_usages`) and show them to the user. Replacing a form's usages repoints every product slot at once and changes live checkouts; it needs explicit confirmation, omitting the replacement form clears the slot, and it cannot be undone automatically. Deleting a form is refused while products use it. Deleting a section is refused while any form includes it, and the error lists those forms: remove the section from them first with `update_product_form`.

Make only the changes the user requested and respect the host's confirmation requirements. After a successful write, summarize the form or section, the returned IDs and the products affected. On Lueira's admin MCP, deleting a form or section and replacing usages only create pending actions the signed-in member confirms: say they are waiting for that confirmation.

Documents customers sign are separate from forms. A document template can be renamed or given a different signer (the buyer, each participant, or both) when document signing is enabled for the business; documents already generated keep their signer. Creating a template needs a PDF and cannot be done through this connection.

To make a participant fill a form in again, invalidate the submission shown for the order with `invalidate_customer_form_submission`. It needs the sensitive personal-data write permission (`pii:write`), which many connections do not have, and `confirm: true`; finding the submission needs `pii:read`. Find the submission and order IDs from the participant's submission list, confirm with the user, and know that the answers themselves are never shown.

Limits: forms from before reusable sections (version v1) can be read but not created or edited here. Courses are managed with `update_course`, whose `forms` object replaces all three slots at once, so send every slot you want to keep.
