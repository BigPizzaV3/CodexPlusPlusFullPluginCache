# 기획부터 최종본까지

블로그의 설계·쓰기·편집·전달 4단계에 연구보고서의 근거 검토와 통합 문체 보정을 연결한 절차다. 장·절의 순서는 보고 목적에 맞춰 선택한다. 상세 도구는 reasoning-tools.md, 보고 유형은 report-types.md를 읽는다.

## 1. 보고서가 답할 질문

‘무엇을 연구하는가’와 ‘이 보고서를 읽고 무엇을 알거나 결정해야 하는가’를 구별한다. 전력시장 제도 개편 연구라도 목적은 현황 설명, 원인 진단, 대안 평가, 실행계획 중 하나이거나 이들의 조합일 수 있다.

다음 사항을 작업 메모에 짧게 정리한다. 사용자가 이미 제공한 값은 재질문하지 않는다.

| 사항 | 정리할 내용 |
|---|---|
| 목적 | 보고서가 답할 중심 질문과 필요한 판단 |
| 독자 | 의사결정권자·전문가·실무자 등, 알고 있는 개념 |
| 범위 | 시점, 국가·지역, 제도·기술, 포함 및 제외 대상 |
| 근거 | 제공 자료, 추가 조사, 계산 또는 모의 필요성 |
| 결과물 | 보고서 전체·장·절·요약, 분량, 서식, 파일 형식 |

5W3H는 누락 점검 도구로 쓴다. 주체·시점·장소·내용·이유·방법·비용·수량 중 해당 질문에 필요한 요소만 확인한다. 8개를 그대로 목차로 만들 필요는 없다. 분량이 미정이면 주어진 목적을 충족하는 길이로 작성하고 중요한 가정을 알린다.

## 2. 질문에 맞는 논리 구조

아래는 선택 가능한 흐름이며 제목을 그대로 복사하는 서식이 아니다.

| 목적 | 가능한 흐름 | 구조를 바꿀 조건 |
|---|---|---|
| 개념·원리 설명 | 질문 → 정의 → 작동 원리 → 예시 → 적용 조건 | 독자가 개념을 알면 정의를 줄이고 쟁점부터 시작 |
| 현황과 쟁점 정리 | 범위·기준 → 관찰 사실 → 변화와 차이 → 해석 → 남은 쟁점 | 시간 변화가 핵심이면 연대기, 분야 차이면 분류 중심 |
| 원인 진단 | 관찰된 문제 → 가능한 원인 → 검증 근거 → 대안 설명 → 판단 | 자료가 부족하면 원인 확정 대신 가설과 확인 방법 제시 |
| 대안 선택 | 결정 사항 → 평가 기준 → 대안별 근거 → 효과·비용·위험 → 선택 조건 | 독자가 바쁘고 근거가 충분하면 권고안을 앞에 배치 |
| 제도 연구 | 문제와 평가 기준 → 관련 원리·경험 → 국내 적합성 → 대안 → 이행 조건 | 해외 사례를 나열하기보다 평가 축별 비교가 유용할 수 있음 |
| 모의·실증 분석 | 질문 → 자료·방법·가정 → 결과 → 해석·한계 → 시사점 | 짧은 보고는 결과 요약을 앞에 두고 방법을 뒤에 설명 |

각 절의 ‘답할 질문 / 핵심 메시지 또는 검증할 가설 / 필요한 근거 / 다음 절로 넘어가는 이유’를 메모한다. 같은 내용이 여러 절에서 반복되면 역할을 나누거나 합친다. 유사 항목끼리 같은 분류 수준을 유지하되, 보기 좋은 대칭을 위해 불필요한 항목을 만들지 않는다.

## 3. 자료에서 주장으로

핵심 주장마다 자료의 위치와 그 자료로 말할 수 있는 범위를 붙인다. 자료를 요약한 문장과 작성자의 판단을 구별한다. 예컨대 제도 도입 여부를 확인한 자료만으로 제도의 효과까지 입증했다고 쓰지 않는다.

상반된 결과가 있으면 대상·시점·방법·측정 기준을 먼저 비교한다. 자료가 결론에 맞지 않는다고 제외하지 않는다. 결론을 좌우하는 빈칸은 질문하거나 조사를 추가한다. 초안에서는 ‘확인 필요’를 작업 메모에 남길 수 있지만 최종 제출본의 빈칸을 임의 수치로 채우지 않는다.

## 4. 본문 작성

문단의 첫 문장에 판단이나 주제를 놓고 뒤에서 이유를 설명하면 읽기 쉽다. 다만 도출 과정 자체가 중요한 설명, 낯선 개념을 쌓아가는 절, 대안을 비교한 뒤 판단하는 절에서는 귀납적 흐름이 적합할 수 있다.

문단이 맡는 역할은 정의·관찰·설명·비교·검증·한계·제안 중 하나 또는 긴밀한 조합이어야 한다. 앞 문단을 다른 말로 반복하는 문단은 줄인다. 다음 문단에는 새로운 근거, 조건, 논리 단계가 있어야 한다. 독립 항목들은 억지 인과관계로 연결하지 말고 병렬 항목으로 정리한다.

‘따라서’는 앞의 근거가 뒤의 결론을 뒷받침할 때 쓴다. ‘한편’은 주제나 관점을 바꿀 때, ‘그러나’는 실제 대비가 있을 때 쓴다. 접속어를 없애는 것 자체가 목표는 아니다.

## 5. 요약문과 결론

본문의 주요 결과가 정리된 후 요약문을 완성한다. 요약문에는 중심 질문, 주요 결과, 적용 조건, 필요한 결정이 들어가야 한다. 본문에 없는 수치나 강한 판단을 새로 추가하지 않는다.

결론은 목차를 다시 읽어 주는 부분이 아니다. 연구 질문에 대한 답, 근거가 허용하는 판단, 실행 시 고려할 조건을 묶는다. 후속 과제는 이번 분석으로 답하지 못한 부분과 연결한다. ‘지속적인 관심과 노력이 필요하다’처럼 어느 보고서에도 붙일 수 있는 마무리는 구체적인 과제로 바꾼다.

권고가 필요한 경우 제안별로 해결할 문제, 담당 주체, 선행 조건, 기대효과, 비용·위험, 확인 지표를 필요한 범위에서 적는다. 근거 없이 연도별 일정을 만들지 않는다. 병행 가능한 과제와 먼저 끝나야 하는 과제를 구별한다.

## 6. 수정과 전달

논리와 사실을 먼저 고친다. 다음으로 문장을 교정하고, 플러그인으로 자연스럽게 다듬은 뒤, 보존 검토를 한다. 큰 구조를 다시 바꾸었으면 영향을 받은 근거와 인용도 다시 확인한다.

문서 파일을 요청받으면 해당 형식의 문서·PDF·프레젠테이션 스킬을 함께 적용한다. 이 스킬은 논리와 글쓰기 기준이며 HWP 편집 엔진이 아니다. HWP를 렌더링하거나 편집하지 못한 경우 다른 형식의 파일을 HWP라고 부르지 않는다. 표·그림·수식이 있는 최종 문서는 실제 페이지를 확인한다.

## 단계 사이의 연결 확인

자료 수집 전에 질문·가설·필요 자료·수집 방법·분석 방법을 정한다. 자료가 부족하면 추가 조사하고, 예상과 다르면 가설·설명을 수정한다. 원하는 결과를 얻으려고 데이터를 조정하지 않는다.

결정·실행 보고서는 자원 요청 → 실행 계획 → 선택안 → 다루는 원인 → 해결할 문제 → 목적 순서로도 읽어 본다. 연결이 끊기면 문장보다 설계를 먼저 고친다. 자원은 인력·조직·예산·권한, 관리는 일정·협의·조정·점검·평가 중 필요한 것을 포함한다.

논리 전개는 시간, 공간, 비교, 분류, 인과, 순서, 생애주기, 가치 판단, 근거에서 결론, 결론에서 근거, 상반된 견해의 검토 등에서 선택한다. 하나의 보고서 안에서도 절별 질문에 따라 다를 수 있다.
