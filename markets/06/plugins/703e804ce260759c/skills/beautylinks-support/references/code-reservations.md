# コード照合：予約登録

確認版：`source-index.md` の F・B（2026-09-20）。操作説明書 p.9〜15と併用する。根拠のコード断片は `code-excerpts.md` の R1〜R6。

## 電話・店頭予約の完結する案内

入口は「予約一覧 → ＋ 新規予約を作成」。カレンダーの「＋予約」からも進める。

1. 「既存顧客」で対象のお客様を選ぶ。初めてなら「選択なし・新規顧客として作成」で顧客名を入力する。電話番号は任意。
2. 予約日を選び、担当欄がある場合は担当スタッフを選ぶ。公開中スタッフが1人なら担当欄を表示せず自動確定する。
3. 単品またはセットメニューを選ぶ。既存顧客の選択により、該当する顧客別所要時間を計算する。
4. 開始時刻を選ぶ。日・週カレンダーの時間枠から開いた場合は引き継いだ時刻を確認する。月カレンダーからは日付だけ引き継ぐため、開始時刻を選ぶ。
5. プレビューの終了時刻・所要時間・料金・空き状況を確認し「新規予約を登録」→確認画面の「実行する」。
6. 予約詳細へ移動したら顧客・日時・担当・メニュー・料金を確認し、予約一覧／カレンダーへの反映も確認する。

初めての案内ではこの流れを省略しない。特定の項目だけの質問には該当箇所だけ答える。

## 画面が違うときの条件

| 症状・質問 | コードで確認した条件と案内 |
| --- | --- |
| 電話番号を知らない | 空欄で登録可能。番号の入力を必須にしない。入力する場合は数字10桁または11桁を基本とし、ハイフンは保存時に除去される。 |
| +81形式が画面を通るのに保存できない | 画面側は+81を許容するが、料金確認・保存側は数字／ハイフンかつ10〜11桁に制限している。この固定版では両者に差がある。料金プレビューでも同じ正規化処理を使うため、確定前にエラーが出る場合もある。画面側だけから国際形式を推奨しない。 |
| 担当スタッフを選ぶ欄がない | 公開中スタッフが1人なら正常な省略。スタッフ0人なら作成できない。人数が不明なら「公開中スタッフは1人ですか？」と必要なときだけ確認する。権限不足と即断しない。 |
| 空き時間候補がない | 日・週カレンダーの時間枠からの作成では候補を表示しない。月表示からは時刻を手動選択する。通常の新規予約で出ない場合はスタッフ・メニュー選択、読み込み状態、営業時間・勤務を確認。 |
| 既存顧客を選んだ後に名前や電話番号を修正した | 各入力の変更時に顧客の選択IDが解除される。顧客別時間やクーポンを利用するなら、目的のお客様が選択されているか再確認する。名前一致だけで確実に既存顧客へ結び付くとは案内しない。 |
| LINE未登録のお客様 | 新規予約の保存時、既存顧客が見つからなければLINE未連携・未同意の顧客を作成する。予約登録がLINE連携や同意の代わりになるとは説明しない。 |
| クーポンを選んだが作成できない | 画面では既存顧客の選択が必要。クーポンの適用エラーと金額プレビューを確認する。新規手入力だけで適用できると案内しない。 |
| 登録ボタンを押せない | 作成処理中、所要時間／料金の確認中、過去日が禁止、開始時刻が予約不可の場合に無効になる。閲覧者は作成不可。必須項目は顧客名・予約日・開始時刻・メニュー・担当（1人なら自動確定）。 |
| 空いていたのに最後に登録できない | 保存側で同じ枠を再確認するため、別予約が先に成立した場合は登録を拒否する。日時・勤務・最新の予約状態を確認し、別の枠を選ぶ。重複登録を避けるため連打させない。 |
| 過去の施術を登録したい | 通常は過去日の新規予約を拒否する。施術履歴はカルテで案内する。コード内の確認用モードを店舗操作として案内しない。 |

## 表示と保存を区別する

画面：F `app/admin/reservations/new/page.tsx` の `createReservation` が B `api/admin/reservation_pricing_routes.py` の `create_priced_admin_reservation` を呼ぶ。後者は閲覧者禁止、入力、過去日、対応メニュー、空き枠を検証し、予約を保存する。保存成功後に予約詳細へ遷移する。

確認画面の文言は「管理画面のカレンダー・予約一覧・通知に料金内訳まで反映」。これだけでお客様宛てのLINE送信成功を保証しない。保存後の通知処理が失敗しても、成立済み予約を取り消さない分岐がある。

予約変更と備考保存は別操作。予約詳細で表示される変更欄・確定状態を確認し、原本p.14〜15の手順を使う。来店済み・無断キャンセルなどの状態を無視して変更できると案内しない。
